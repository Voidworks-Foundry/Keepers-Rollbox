# Player Rollbox (`scripts/player/`)

Whether players get a Rollbox panel of their own and which features it offers: a Keeper section, Player Rollbox, with a master switch (on by default; off: Rollbox is a Keeper tool only) and one tick box per feature. A player's panel shows only their own investigator, with the menu **Action · Check · Other**, each button shown only when a feature in it is allowed (Check is Characteristic · Skill, with no Sanity tab: Sanity checks are the Keeper's; Opposed and Assist are tabs of Other, with no Luck tab: the Keeper calls for Luck rolls, Keeper Rulebook p. 90). A player makes their own checks (Make check) on their own client, rolled at once by CoC7 with no window ([roll-requests.md](roll-requests.md), `makeCheck`). Players pick opponents and helpers by targeting tokens, since they can't select others. This part also lists the players' assigned investigators for the Keeper's panel with nothing selected (`investigators`). Files: `index.js` (the switches, the player's menu, their character, the players' investigators), `targeting.js` (the targeting prompt), `targeting.css` (its look).

User guide: [For players](../guide/for-players.md) (what a player sees), [For Keepers](../guide/for-keepers.md) and [Settings](../guide/settings.md) (turning it on, the feature tick boxes).

**Status key:** *Confirmed* only when the [Internal API registry](DEVELOPING.md#internal-api-registry) says so. The player's panel, a flyout on their client, an opposed roll through the Keeper, a feature turned off live and Cancel on a pick were seen working in Foundry (build 370) in the end-to-end check, with the demo's Player assigned Helen; still **Assumed** until checked at the table.

## Code

### `playerRollboxOn()` (`index.js`)
- **How it works:** `option("rollboxPlayerRollbox") === true`: the world's master switch. Read through `utils.js` `option()`, so it answers with the declared default (on) until settings.js registers it.
- **Connects to:** `panelHere()` below; `panel/index.js` `registerPanel()`, `roll-requests/` `registerKeeperRelay()`, `combat/` `registerCombat()`, the alert's `registerBeingAttacked()` and `settings.js` (`decorateSettingsConfig`, which hides Rollbox's settings from players while it is off).
- **Could interact poorly with:** nothing known. **Assumed.**

### `panelHere()` (`index.js`)
- **How it works:** whether this client runs a Rollbox panel: the Keeper's, or a player's with the Player Rollbox on, and in both cases only with the user's own "Rollbox panel" (`rollboxEnabled`) on, so a player can turn Rollbox off completely on their screen. The Keeper test comes first, so a player with the Player Rollbox off reads nothing else.
- **Connects to:** every flyout's `register…()` (Action, Check, Other, Opposed), combat's turn order (`registerCombat`), the alert (`registerBeingAttacked`). `panel/index.js` `registerPanel()` makes the same test itself.
- **Could interact poorly with:** nothing known. **Assumed.**

### `panelOnFor(user)` (`index.js`)
- **How it works:** whether another user has their own "Rollbox panel" (`rollboxEnabled`, user scope) on, read on the Keeper's client. Foundry keeps every user's user-scope settings as `Setting` documents in the world collection (`game.settings.storage.get("world")`), and `getSetting(key, userId)` finds one user's; a Keeper's client holds every user's (seen in a probe of the test world). No document means the user never changed it: the default, on. Anything unreadable counts as on. Assist's `rollsOnPanel` uses it, so a player who turned their own panel off gets CoC7's chat request instead of a Roll button they can't see.
- **Connects to:** Foundry's `ClientSettings#storage`, `WorldSettings#getSetting` (build 370 `client/documents/collections/world-settings.mjs`); `flyouts/other/assist-group.js` `rollsOnPanel`.
- **Could interact poorly with:** a Foundry that stops sending other users' settings to a GM: every player counts as panel on, so a player with their panel off is offered a Roll button they can't see. Internal API registry. **Assumed.**

### `canUse(feature)`, `playerFeatureOn(feature)`, `PLAYER_FEATURES` (`index.js`)
- **How it works:** For `feature` in `PLAYER_FEATURES` (`actions`, `checks`, `combined`, `sanity`, `luck`, `opposed`, `assist`): `true` for the Keeper (`isKeeper()`) whatever the switches say; for a player, `true` only with the master on and that feature's setting (`rollboxPlayerActions` … `rollboxPlayerAssist`) on. `combined` also needs `checks`: combined checks are a way of making checks, so without Checks they give nothing. An unknown feature is `false` for everyone, the Keeper included, so a misspelt name shows up at once rather than working only for the Keeper. Always about the current user (`game.user`). `playerFeatureOn(feature)` is the player half on its own (the master and that feature's tick box, never `KEEPER_ONLY`), the same on every client: the Keeper's client uses it to check what a player asks for through the relay (Assist's join and leave).
- **Connects to:** `offersMenu`, `offersClick`, `playerMenu` below; the flyouts, which ask it which tabs a player gets (Action: `actions`; Check: `checks` for the Characteristic and Skill tabs, and never a Sanity tab; Other: `opposed`, `assist`, one per tab). `sanity` and `luck` are still features `canUse` knows, for the Keeper's saved settings, but `KEEPER_ONLY` makes both false for every player whatever their tick box says, so nothing a player sees offers them. `combined` is read by the Check flyout: without it a player ticks one check at a time ([check-flyout.md](check-flyout.md)); the menu and the sheet clicks don't read it. The Check flyout also asks `opposed`, for a row's right click.
- **Could interact poorly with:** nothing known. **Assumed.**

### `offersMenu(id)`, `playerMenu()`, `PLAYER_MENU` (`index.js`)
- **How it works:** Each menu id has its features: `action` → actions; `check` → checks (Combined checks alone gives no Check button); `other` → opposed, assist; and `opposed` → opposed, `assist` → assist, for a click that names one of those places (`offersClick` falls back to `offersMenu`). `offersMenu(id)` is true when any of its features is allowed (always for the Keeper; false for an id it doesn't know). `playerMenu()` is `PLAYER_MENU` (`action`, `check`, `other`) filtered by `offersMenu`: empty with the master off.
- **Connects to:** `panel/index.js` `redraw()`, which passes `playerMenu()` to the menu host's `update(actors, ids)`, so a player's panel draws only those buttons.
- **Could interact poorly with:** nothing known; a player's menu never has the Keeper's extra Opposed button (Opposed is a tab of their Other). **Assumed.**

### `offersClick(action)` (`index.js`)
- **How it works:** Whether a click on the character sheet may do what `panel/sheet-clicks.js` `shortcut()` asks: an opposed side (`action.opposed`) needs Opposed; Check on its Sanity tab (SAN) is never allowed for a player (Sanity checks are the Keeper's), so a player's click on SAN does nothing; Other on a section (Luck, from the sheet's Luck) needs that section's own feature, which a player never has for Luck, so a player's click on Luck does nothing too; any other Check (a characteristic) needs Checks; anything else falls back to `offersMenu`. True for the Keeper; false for no action.
- **Connects to:** `panel/index.js` `onValue()`.
- **Could interact poorly with:** a new shortcut that opens another flyout: it is allowed when `offersMenu` knows the flyout's id, and refused otherwise. **Assumed.**

### `ownCharacter(user)` (`index.js`)
- **How it works:** Foundry's `User#character` (the character assigned in the user's configuration), only when the user owns it (`Document#testUserPermission(user, "OWNER")`, public), since a player can roll only for characters they own. `null` for no user, no character, a character they don't own, or one that throws (one warning).
- **Connects to:** `panel/index.js` `playerActors()`: a player's panel shows this character whatever is selected; `combat/turn-order.js` (the player's own turn row); the alert (`flyouts/alert/being-attacked.js`: whose attack cards to watch).
- **Could interact poorly with:** a player who plays two characters: only the assigned one shows. **Assumed.** A character assigned but not owned (Foundry lets a user be assigned a character with only Observer): no panel character; the player sees the panel's no-investigator message ([panel.md](panel.md)). **Assumed.**

### `investigators()` (`index.js`)
- **How it works:** Each player's assigned investigator that they own: `ownCharacter(user)` (Foundry's `User#character`, only when the user owns it) of every non-GM user in `game.users`, in that order, each character once (by uuid), with the first player it is assigned to, as `[{ actor, user }]`. A character assigned to a player who doesn't own it isn't listed, the same as their own panel shows no character. A throw while reading is one warning and gives what was read so far.
- **Connects to:** `panel/index.js`: with nothing selected the Keeper's panel lists them (`panel/cards.js` `playersList`, personal setting `rollboxShowPlayers`), and the Check and Other flyouts act for all of them ("Send to all players"); the `updateUser` hook redraws the list when any player's assigned character changes ([panel.md](panel.md)).
- **Could interact poorly with:** two players assigned the same character: it is listed once, with the first player. **Assumed.**

### `SETTINGS` (`index.js`)
- Declared with `declareSettings` (section `playerRollbox`, world scope, Keeper note), the switch first: `rollboxPlayerRollbox` ("Player Rollbox", the feature switch at the top of the settings page, hint "Players get their own Rollbox panel, with their own investigator and the features ticked in the Player Rollbox section below.", default **on**: Rollbox is a tool for both sides of the table, and a world where the Keeper switched it off keeps its saved value), then `rollboxPlayerActions` ("Actions (attacks, maneuvers, spells)"), `rollboxPlayerChecks` ("Checks"), `rollboxPlayerCombined` ("Combined checks", hint "Only with Checks on: without Checks it gives nothing. Off: a player ticks one check at a time."), `rollboxPlayerSanity` ("Sanity") and `rollboxPlayerLuck` ("Luck"), both registered with `config: false`: not shown in Configure Settings and read by nothing (players have no Sanity or Luck tab; `KEEPER_ONLY` makes `playerFeatureOn` false for both before their settings are read), kept registered because their keys are permanent and their saved values stay ([settings.md](settings.md)), `rollboxPlayerOpposed` ("Opposed rolls"), `rollboxPlayerAssist` ("Assist"), all default **on**, so players get the whole panel. The keys are permanent once released.

### `pickTarget({ prompt, parent, useCurrent, restore })`, `targetedToken()`, `cancelPick()`, `picking()` (`targeting.js`)
- **Already targeted = use it:** with `useCurrent` (the default) a token the player has targeted already (`targetedToken()`, their first Foundry target) is used at once, with no prompt. Callers pass `useCurrent: false` to always ask: the Action flyout's Change, Opposed when that character is already a side, Assist when they're already in, and a player's Target who you're helping (with `restore: true`: once the token is picked, the targets from before are put back, since the pick only says who).
- **How it works:** Otherwise puts a prompt (`.rollbox-targeting`: the line, default "Select your target", and a **Cancel** button, `role="status"`) at the top of the screen (`#interface`, else `body`), or inside `parent` when given (the Action flyout's target box). Remembers the scene controls' current control and tool (`ui.controls.control.name`, `ui.controls.tool.name`), then switches to the Token layer's Target tool with `ui.controls.activate({ control: "tokens", tool: "target" })`, exactly as the player's own click on that tool would. Foundry's own targeting does the rest: a click on any token targets it (players may target tokens they can't select). Listens to Foundry's `targetToken` hook and resolves with the first token **this user** targets (other users' targets and released targets are ignored). Then removes its hooks and the prompt and puts the earlier tool back (or Select, if it started from the Target tool). The target stays targeted: CoC7's attack cards read `game.user.targets`.
  - **Cancel** (its button, **Escape** while the prompt shows, or `cancelPick()`): resolves `null`, puts back the targets the player had before the pick (`canvas.tokens.setTargets(ids, { mode: "replace" })`) and puts the tool back. Escape: a capture-phase `keydown` listener on `window` for as long as the prompt shows, which takes that key press (one press, one thing closed: the panel's own Escape yields while `picking()`). `picking()`: whether a pick waits now.
  - **Ends with `null` too** when the scene closes (`canvasTearDown`), when another `pickTarget` starts (one prompt at a time), or when switching to the Target tool fails (one warning).
  - **Does nothing** (one warning, resolves `null`, no prompt) without `canvas.tokens`, `ui.controls.activate` or `Hooks`.
- **Connects to:** the Action flyout's target box (`flyouts/action/target.js`), the Opposed view (`flyouts/opposed/index.js`) and Assist (`flyouts/other/assist.js`) on a player's Other flyout, which call it to pick a target, an opponent or a helper (through `player/index.js`); Opposed and Assist also read `targetedToken()` first. Foundry's `SceneControls#activate`, `targetToken` and `canvasTearDown` hooks, `game.user.targets` and `TokenLayer#setTargets`.
- **Could interact poorly with:** modules that add their own targeting tools or change the Token layer's tools: if `tokens`/`target` is renamed, switching fails and the pick ends with `null`. **Assumed.** Modules that target tokens for the user (e.g. auto-targeting on hover): their first target resolves the pick. **Assumed.** Foundry's own **T** key over a token works during a pick (it fires the same hook). **Assumed.**

### `targeting.css`
- The prompt's look: Foundry's own colours (`--color-cool-5`, `--color-cool-3`, `--color-light-1`, with fallbacks), since it sits outside the panel and its palette. At the top centre of the screen (`position: fixed`) when it is in `#interface` or `body`; in the flow of its `parent` otherwise. Listed in `module.json` `styles`.

## Hooks, overrides, keybindings
- `targetToken`, `canvasTearDown` (Foundry public hooks): only while a `pickTarget` is waiting, removed when it ends.
- Through `panel/index.js` on a player's client with the player Rollbox on: `updateUser` (redraw when this user's assigned character changes, so the panel appears once one is assigned), plus the panel's own hooks. On the Keeper's client the same hook redraws the players list when any player's assigned character changes.
- No overrides, no keybindings.

## Settings
Declared here, registered by `settings.js`: the switch among the features on top, the features in the Player Rollbox section (with a player's own Roll my attacks at once), which greys out while the switch is off. Only the master `rollboxPlayerRollbox` has `requiresReload: true` (a player's client decides at `ready` whether to build a panel); the features apply at once: their `onChange` (which Foundry runs on every client for a world setting) redraws the player's menu (`panel/index.js` `refreshPanel`), and the flyouts read them each time they're drawn. `index.js` also re-exports `pickTarget` and `targetedToken` for other parts.

## A player's requests
A player's own checks are not requests: Make check calls `roll-requests/` `makeCheck`, which has CoC7 make the check on the player's own client at once (CoC7's actor check with `fastForward`: no window, its card posted). Their other flyouts send through `roll-requests/` `send()` as the Keeper's do. A request for their own characters goes out from their own client; an opposed card, an NPC or another player's character goes to the Keeper's client through Rollbox's socket (`roll-requests/relay.js`, [roll-requests.md](roll-requests.md)). An NPC in what a player starts is rolled privately on the active Keeper's client at once (never a CoC7 link whispered to the Keepers, which names no character); only an opposed card's Start rolls is left to the Keeper. With no Keeper online the player is told "Rollbox: the Keeper needs to be online for this." and nothing happens. CoC7's Keeper-only toggles on a player's attack card (Aiming, Reloading, Under cover, Point blank, In melee, Outnumbered, the dice) are set by the Keeper's client the same way, and the weapon-drawn notice a player's draw calls for is made by the Keeper's client ([combat.md](combat.md)).
