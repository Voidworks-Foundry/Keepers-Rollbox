## How to use these notes

- **Before changing code:** read the sections that touch your change, especially the CoC7 sections and the Internal API registry.
- **When you learn something** (a Foundry or CoC7 behaviour, a rule that caused a bug, a new internal API in use): add it to the section for its topic.
- **When these notes and the code disagree:** stop and ask in an issue; don't guess which one is right.
- **(confirmed)** means verified in Foundry. **(assumed)** means inferred from docs or source and not yet tested in play.
- The maintainer is Voidworks Studios. A rule or behaviour these notes state is a deliberate choice: don't "fix" it without asking in an issue. Code comments never carry names or dates; they say why instead.

## Setup

The repository root is the module folder (`keepers-rollbox/`, holding `module.json`). Foundry ignores everything in it except `module.json` and `scripts/`.

```
npm ci                                                       # the test tools: jsdom, fflate (dev dependencies only)
npm test -- tests/<file>.test.mjs                            # one test file
npm test -- --test-name-pattern="<pattern>" tests/<file>.test.mjs   # one test or group (pattern before the file)
npm test                                                     # every test
npm run release-check                                        # builds dist/keepers-rollbox-v<version>.zip, then checks it
```

`package.json` also has `npm run package` (the zip only) and `npm run smoke` (check an existing zip); `release-check` runs both. [TESTS.md](TESTS.md) gives every test's pattern. If your shell's `npm` won't pass a pattern with spaces, run `node --test --test-force-exit --test-reporter=spec --test-name-pattern="<pattern>" tests/<file>.test.mjs` directly.

**Try a build in Foundry:** run `npm run release-check`, return Foundry to its setup screen, remove any installed `Data/modules/keepers-rollbox`, unzip `dist/keepers-rollbox-v<version>.zip` into `Data/modules/` (it holds one `keepers-rollbox` folder), launch a CoC7 world and enable Keeper's Rollbox. Foundry reads `module.json` (its `esmodules`, `styles` and `socket`) only when a world launches: after adding, moving or renaming a script or stylesheet, return to setup and launch the world again; F5 isn't enough.

## Same standard as void-coc7-modules

Rollbox is built the same way as the maintainer's other CoC7 module (`void-coc7-modules`), so the two can be merged into one module later. Keep to these conventions even where they look like more structure than one module needs.

What must match:
- **One folder per part** under `scripts/`, holding `index.js` (the part's `register…()` functions and logic, and its public surface), its settings (a `settings.js`, or a `SETTINGS` list made with `declareSettings()` in the file that uses them), any other files the part needs, and its CSS. Nothing about a part lives outside its folder except its test file, its document, and one line each in `main.js` and `settings.js`.
- **`scripts/main.js`** holds wiring only, in the same shape: `Hooks.once("init", …)` registers settings; `Hooks.on("renderSettingsConfig", decorateSettingsConfig)`; `Hooks.once("setup", …)` or `Hooks.once("ready", …)` calls each part's `register…()`.
- **`scripts/settings.js`** started as the CoC7 module's file, copied. Each part exports its settings as plain data (`declareSettings` lists, or objects keyed by setting: `{ name, hint, scope, type, default, note, requiresReload? }`); `settings.js` lays them out in its own `FEATURES` and `SECTIONS` (features on top, each section greyed by its feature, see "Settings"). Registration defaults to `requiresReload: true`. The italic scope notes, Reset buttons and headings are the same code; the per-section master switches of the CoC7 module's copy became Rollbox's feature switches, a difference to settle when the two merge.
- **`scripts/utils.js`** starts with the same `MODULE_ID`, `KEEPER`, `PERSONAL`, `escapeHtml()` and `getSetting()`; Rollbox's own shared helpers go after them.
- **Tests:** `tests/mocks.mjs` with `makeEnv()` and `load()` in the same shape (extended with what Rollbox needs), and one `tests/<part>.test.mjs` per part. `package.json` runs `node --test --test-force-exit --test-reporter=spec`.
- **Part documents** in `docs/<part>.md`, in one format: a title with the part's path, a short intro, the status key, then `## Code` with one `### \`name()\`` entry per exported function, hook, class and override, and per private function that touches Foundry or CoC7 (other private helpers get no entry; their JSDoc says what they do), each with **How it works**, **Connects to**, **Could interact poorly with**, every interaction marked **Confirmed** or **Assumed**; then `## Hooks, overrides, keybindings` and `## Settings`. A part document says how the part works now; its history is in the CHANGELOG.
- **`CHANGELOG.md`:** `## <version>` headings, newest first, with one plain-words bullet per change ("Fix: …", "Internal: …", or the feature).
- **`module.json`:** the same fields (`id`, `title`, `description`, `version`, `authors` [the maintainer], `compatibility` 14/14, `relationships.systems` CoC7, `esmodules` ["scripts/main.js"]), plus `styles` for Rollbox's CSS and `"socket": true` for the Keeper relay.

So a merge stays simple, Rollbox keeps everything namespaced:
- Part folders have specific names (`panel/`, `roll-requests/`), never generic ones such as `ui/` or `core/`.
- Setting keys start with `rollbox` (`rollboxEnabled`).
- CSS classes start with `rollbox-`, CSS variables with `--rollbox-`.
- Template paths are built from `MODULE_ID`, never typed out (Rollbox has no templates today).

Merging later means: copy the part folders, add their sections to the CoC7 module's `SECTIONS` and their `register…()` calls to its `main.js`, and move any Rollbox helpers into its `utils.js`. Saved Rollbox settings reset at that point, because the module id changes.

- **A new part gets its own folder** (a new flyout goes under `scripts/flyouts/<name>/`, one file per tab, its document `docs/<name>-flyout.md`). `main.js` calls its `register…()` from the right hook.
- **A part's settings** are declared with `declareSettings()` (`utils.js`) and exported as `SETTINGS`; `settings.js` gathers them into its sections. `option(key)` reads one safely, also before `settings.js` has registered it. A new part that isn't ready yet can start as its interface: exported functions with JSDoc and a body that returns a safe nothing (empty list, `null`, `false`), not called from `main.js`.
- **Another part draws the character panel** through the panel's `setPanelContent(provider)` (combat's turn order does), never by editing `panel/`.
- **Anything two parts share** goes in `utils.js` (small helpers every part may need), in `shared/` (flyout controls and their CSS), or stays in the part that owns it and is exported from its `index.js`: flyouts send through `roll-requests/` and never build CoC7 requests themselves; skill names are matched only by `skill-values/`. A part imports another part's `index.js` only, never the files beside it (`shared/` too: its `index.js` re-exports the controls; the module's `settings.js` reads each part's settings through its `index.js` too, except the panel's (`panel/settings.js`, whose settings call the panel's own functions when they change, so a re-export would make an import cycle)). There is no other exception: `flyouts/flyout.js` takes `blindToggle`, `withBlind`, `statusLine`, `button` and `glyphButton` through `shared/index.js` like every other part (no `shared/` file imports a flyout, so there is no cycle).
- **No build step.** Files load as native ES modules. Every part builds its DOM in JS with `textContent` (no Handlebars templates); `release-tools` still checks template paths, for `void-coc7-modules`.

## Lifecycle: which hook does what

| Hook | Runs | Put here | Don't put here |
| --- | --- | --- | --- |
| `init` | Once, first | `game.settings.register`, `game.keybindings.register`, CONFIG changes that need no settings | `game.settings.get` for world settings |
| `setup` | Once, before the canvas draws | Read settings; subclass CONFIG classes; install feature hooks | Anything needing `game.users` state or the canvas |
| `ready` | Once, everything loaded | Work needing users, the canvas, the players list, CoC7's APIs | Class swaps (too late) |
| `canvasReady` | Each scene load | Per-scene setup | One-time setup |

`main.js` registers the settings at `init` and starts every part at `ready` (the Keeper relay, the panel, the flyouts, combat, the being-attacked alert). Only install a hook when its feature is on, and only on a client that needs it: the Keeper's, or a player's while the Keeper has turned on the Player Rollbox (`player/` `panelHere()`). With the Player Rollbox off, a player's client runs no Rollbox code beyond registering settings and hiding Rollbox's tab in Configure Settings. Permanent hooks are never removed: the panel's switch and the Player Rollbox switch need a reload, so there is nothing to clean up; a temporary hook (watching for a card) removes itself.

## Changing core behavior

Use the least invasive tool that works, in this order, and never replace a core or CoC7 method outright.

1. **A hook** (`Hooks.on(...)`), when Foundry or CoC7 offers one at the right moment.
2. **Subclass the current CONFIG class** (read it at `setup`, extend that value, call `super`).
3. **libWrapper**, only for methods no CONFIG class exposes, and only after the maintainer agrees (it's a dependency).
4. **Never assign over a prototype method.** It silently breaks any other module touching the same method.

**Stay in Rollbox's lane**: never intercept, override or change CoC7's or Foundry's own behaviour (clicks, rolls, cards, dialogs). Rollbox only sends requests through their normal paths. If something they do is awkward, write it up in an issue; don't work around it.

### Which APIs we may call

| Kind | Looks like | Rule |
| --- | --- | --- |
| Public | `canvas.tokens.controlled`, `ChatMessage.create` | Use freely |
| Protected | `_onRender`, `_prepareContext` | Call or override only from inside our subclass |
| Internal | Underscore properties, CoC7 classes not meant for modules | Only if nothing public works. Guard against it being missing, and list it in the Internal API registry |
| Undocumented | Anything not in the [v14 API docs](https://foundryvtt.com/api/) or CoC7's source | Don't use |

**Guard every internal read** so a Foundry or CoC7 update degrades to "feature does nothing" (with one `console.warn`) rather than an error.

## Multiplayer

- **Rollbox runs only on the Keeper's client, unless the Keeper gives players a Rollbox** (Player Rollbox): then a player's client runs the panel, flyouts, turn order and alert (`player/` `panelHere()`), and anything CoC7 needs a GM for goes to the Keeper's client through the module socket (`roll-requests/relay.js`). Check `game.user.isGM` (or `panelHere()`) before installing hooks or drawing anything. `User#isGM` is true for both the Gamemaster and Assistant GM roles (v14 docs), so `isKeeper()` lets Assistant GMs see the panel too. (assumed)
- **Requests to players** are whispered to the owners of each character (users with OWNER permission on the actor, not GMs). There is no public request and no copied link.
- **NPC sides** (no player owner) roll automatically for the Keeper, privately.
- **Hook data from other users is untrusted.** Names go into chat HTML; escape them, never insert raw user-written HTML.
- **Two GMs logged in:** every GM client runs the Keeper's hooks, so anything that writes or rolls (combat's round start, a pick mid-round, the relay, the Under cover tick) acts only on Foundry's active GM (`utils.js` `isActiveKeeper`, `game.users.activeGM`); drawing and the Keeper's own clicks stay on every GM's client.
- **A player's socket message is untrusted too:** the Keeper's client takes the sender from Foundry's server (none: ignored), rebuilds the request with `requests.js`, refuses a type Rollbox doesn't make, and sends only for characters the player plays (or, for Assist, with one of theirs helping, and only when the rollers have no player or the helpers stand in the rollers' Assist group with the player's own investigator: a list of uuids in a socket message proves nothing by itself).
- **A message flag is untrusted unless its author may write it** (reproduced): any user can create a chat message carrying `flags.keepers-rollbox.*`, so a flag that makes the Keeper's client act (the maneuver notice) is read only when `ChatMessage#author` is a GM or a player of the character the flag speaks for. A player's own notice is written from their client, so "GM author only" would break their own maneuvers.
- **Draw gun is a toggle:** CoC7's tracker button flips `hasGun`, so a press made on every GM's client cancels itself out with two GMs. Every Draw gun press (`readied-firearms.js`) and every write from a hook that fires on every client (`deleteCombat`'s picked weapons cleared) runs on the active GM only.
- **`game.combat` is the encounter the client views, not the one that runs** (Foundry build 370, read in `client/game.mjs` and `combat-encounters.mjs`): `game.combat` is the tracker's viewed combat (`ui.combat.viewed`), and `game.combats.active` and `CombatEncounters#combats` only cover `game.scenes.current`, which is the **viewed** scene once the canvas is ready. A Keeper who looks at another scene mid-fight has neither. Rules that must keep running read the started combats of `game.combats` (`combat/encounter.js` `runningCombat`, by the characters concerned); only what is drawn for the viewed scene reads `game.combat` (`viewedCombat`). A character's tokens on other scenes come from `Actor#getDependentTokens()` (public; `getActiveTokens` is the viewed scene only). Reproduced: before the fix a standing-by turn wasn't skipped and Unconscious wasn't marked defeated with the Keeper on another scene.
- **A flag's object written from two clients merges per key** (Foundry's update merges objects; arrays and other values are replaced): a note several clients mark (round notes: a player's attack, the Keeper's defence) writes only the keys it changes, never a whole copy read before the other client's write landed, not even for the round's first mark (over a note left from an earlier round only its own keys are written off).
- **`-=key` deletes are deprecated in v14** (`common/utils/helpers.mjs` `_migrateDeletionKey`: a compatibility warning since 14, until 16): an update that removes a flag beside other changes uses `foundry.data.operators.ForcedDeletion` (`_del`, what `unsetFlag` itself sends), through `utils.js` `flagsRemoved`. Hooks then see the key with a `ForcedDeletion` value, so a reader tests `key in flags` (both forms), never the value.
- **Foundry sorts equal initiatives by id** (`Combat#_sortCombatants`, build 370): nobody can be placed between two tied combatants, so Delay passes a tie group as one stop.
- **One action per document in flight:** a relayed answer that reads a flag and then writes it (`answer` on the notice) can run twice before the first write lands; keep an in-flight set per document on the client that acts.

## Performance

| Hot path | How often | Rule |
| --- | --- | --- |
| `controlToken` hook | Every selection change, once per token (a box-select fires it many times) | Don't redraw per call: coalesce to one redraw on the next animation frame |
| Panel render | On selection change and flyout actions | Render only the visible part; no work while the panel is hidden |

- Read settings outside hot paths; early-return first (`!game.user.isGM`, switch off, nothing selected).
- No `await` inside `controlToken`; schedule the redraw instead.

## Rules and units

- Rule pages are from the Call of Cthulhu 7th Edition Keeper Rulebook. Cite the page for any rule implemented in the feature's design file (its Rules section); a code comment names a page only as part of a short why.
- **Base skill values** (for skills missing from a sheet) live in one table, `scripts/skill-values/base-skills.js`, citing the Keeper Rulebook skill list (p. 56). Dodge = half DEX; Language (Own) = EDU; both rounded down, as CoC7 does. Checked against CoC7's Skills compendium: no value differs (`docs/skill-values.md`).
- **Trained** = on the sheet and above Rollbox's table value, never `system.adjustments.base` alone (see "Actor and item data").
- **No skill is hidden by era, or at all**: games move between eras. Every table skill is always offered, Modern-era ones (Computer Use, Electronics) included. CoC7's per-era skill tags are incomplete (its Dark Ages list lacks Listen; Invictus lacks Dodge), so they are not used.
- **Opposed rolls:** exactly two sides; no difficulty, bonus or penalty dice only (p. 92); can't be pushed (p. 90); tie goes to the higher skill (p. 91). CoC7's opposed card does the comparing.
- **Combined rolls:** one character, one roll, compared with each chosen check; "all" or "any" (p. 92).
- **Assist (Physical Human Limits, p. 88–89, summary p. 407):** plain arithmetic, no Foundry calls (`flyouts/other/assist-split.js`): helpers lowest first; what's left must stay above 0 and be at most 100 + each remaining character's value; difficulty from what's left (50+ Hard, 90+ Extreme); the best chance that at least one roller succeeds wins, ties to fewer helpers. The chance (value, half or fifth over 100) is only an estimate for choosing; CoC7 rolls and judges the real rolls.

## Code style

- Native ES modules, `import`/`export`, no globals. The only top-level side effects are in `main.js`.
- `MODULE_ID` from `utils.js` everywhere; never retype the id string.
- Named functions over anonymous blocks, each doing one thing. Files stay under about 450 lines; a part that grows past that is split into files in its folder, with `index.js` re-exporting its public surface.
- **Comments:** a file header of at most 3 lines (what the file does, and its part document); JSDoc on every export, a one-sentence summary of at most 2 lines with `@param` and `@returns`; inline `//` only for a real why (a CoC7 or Foundry quirk, an order, a race, a security check), at most 2 lines; comment lines at most a quarter of a file's code lines; no history, names, dates or build numbers. What a feature does goes in DESIGN.md, how a part is built in its part document. `tests/comments.test.mjs` checks the sizes.
- Constants, not magic numbers.
- Write each template path whole, in one string: `` `modules/${MODULE_ID}/scripts/<part>/<name>.hbs` ``. The smoke test finds template paths written that way and fails the release if the file isn't in the zip; a path put together from pieces isn't checked.
- Console messages go through `warn(text, ...details)` in `utils.js`, which adds the `keepers-rollbox |` prefix; a caught error goes in as a detail (`warn("the Check flyout failed to draw.", error)`). No part calls `console.warn` itself.
- 2-space indent, double quotes, semicolons, lines under about 120 characters.

## Testing

Every change passes the unit tests before it is merged, then the e2e check in a running Foundry, and the Foundry check (below) before a release.

### Unit tests

- `npm test` (from the repository root, the module folder) runs Node's built-in test runner (`node --test --test-force-exit --test-reporter=spec`). It runs every test even when one fails and names each test; `--test-force-exit` ends each file once its tests are done, so a real timer a test left running (the attack card's 15-second watch) doesn't hold the run open.
- Tests use mocks of `game`, `CONFIG`, `Hooks`, `canvas`, `ChatMessage` and the parts of CoC7 we call, in `tests/mocks.mjs` (same `makeEnv()` / `load()` shape as the CoC7 module). DOM tests use `jsdom`; every DOM test makes its page with `makeDom()` (`mocks.mjs`).
- Add tests with every feature or fix, including the "does nothing" paths: switch off, not the Keeper, nothing selected, a token with no actor, CoC7's API missing.
- **Mocks prove our logic, not Foundry's or CoC7's.** Anything relying on how they behave stays marked assumed until checked in play.
- **jsdom and tick boxes:** `input.click()` on a checkbox fires `change` only when the element is in the document. Append a flyout's body to `document.body` before clicking.
- **jsdom and CSS:** jsdom does no layout (`offsetHeight` is 0) and its `getComputedStyle` returns the declared value: `var()` and `calc()` are not worked out, shorthands such as `gap` are not split into `rowGap`, and a custom property is read only on the element that declares it. A test of a CSS rule loads the stylesheet (`addStyles` in `mocks.mjs`) and checks the declarations, e.g. that a list's `max-height` and its rows' `height` use the same variable; a test that needs a height stubs `HTMLElement.prototype.offsetHeight`.
- **Timers:** a test file whose code waits on `setTimeout` (the card buttons' click delays and their 15-second watch) uses Node's own fake timers: `mock.timers.enable({ apis: ["setTimeout"] })` in `beforeEach`, `mock.timers.reset()` in `afterEach`, and `mock.timers.tick(ms)` to run them. One `tick` runs only the timers due when it was called, not ones they schedule, so a retry loop needs one `tick` per try. A pending real timer keeps the test file open until it fires (an Opposed flyout test would wait 15 s for the watch). Let a send finish with `await new Promise(setImmediate)`: the mocked CoC7 calls are promises only.
- **Looks in a real browser:** a scratch harness can draw the real panel with jsdom and the test mocks, write it out as a static page, and open it in headless Chrome (`chrome --headless=new --allow-file-access-from-files --screenshot` or `--dump-dom` with a script that writes measurements into the title). Load Foundry's own `resources/app/public/css/foundry2.css` and `public/fonts/fontawesome/css/all.min.css` from the install, with `<body class="vtt game theme-dark">`, and the module's stylesheets through `@import url(…) layer(modules)`, so fonts, variables, tick boxes and the cascade layers are Foundry's (without them the character sheet measured 184px instead of 182px). Input values must be copied into `value` attributes before serialising. Give each Chrome run its own `--user-data-dir` and wait for it (pipe its output), or the screenshot is lost. It never goes in the repo.
- **A `<label>` row with a tick box** gets two `click` events for one click (the label's, then the box's synthetic one); cancelling the label's click cancels the box's toggle, so a modifier-click handler on the label can turn the click into a shortcut without the box changing.
- **Module state outlives jsdom pages in the tests:** a card kept in a module variable (`fight-boxes.js` `joiningCard`) is still `isConnected` in the last test's page, so a test that wants a fresh card closes it first (`closeJoiningCard()`).
- **`docs-index.test.mjs`** keeps the index true: it fails for a test file without its `## <file>` section in [TESTS.md](TESTS.md), a part folder without its document (`docs/<part>.md`, a flyout's `docs/<name>-flyout.md`), or a path in `AGENTS.md`'s "Find your way" section that doesn't exist. The sections' pattern tables are built from the test names.

### The e2e check (development repository)

Unit tests with mocks can't show how Foundry and CoC7 really behave, so every change is also run end to end in a real Foundry. The e2e check lives in the development project, in `tools/e2e/` beside the module folder (not in this repository, and never shipped); its `README.md` there says how to run it and how to add a step.

- **What it is:** Playwright (its own `package.json` and dev dependency; installed Google Chrome, or Playwright's Chromium) driving the test world "Call Of Cthulhu", with the demo setup, in a running Foundry at `http://localhost:30000`. It logs in as the Keeper (user Capture) and as Player, and runs areas of steps: `keeper-one`, `keeper-two`, `keeper-group` (one, two, three or more tokens), `panel` (moving, Tab and Escape, the Panel layer, auto-hide), `combat`, `themes`, `action`, `settings`, `player`, and `review` (screenshots only, run only when named).
- **Run:** `npm --prefix tools/e2e install` once, then `npm --prefix tools/e2e run e2e` from the project folder (from PowerShell, `npm.cmd`), optionally naming areas (`… run e2e -- keeper-two player`). `E2E_BUILD` names the folder the screenshots go to; `E2E_HEADED=1` shows the browser. Passwords, only if the world asks: `FOUNDRY_CAPTURE_PASSWORD`, `FOUNDRY_PLAYER_PASSWORD`, from the environment only.
- **Output:** one `PASS` or `FAIL` line per step, a total, exit code 1 on any failure. A page error or a `keepers-rollbox |` console error during a step fails it; a failed step saves full-page screenshots of both users.
- **It puts the world back,** even after a failure: menus closed, tokens released, the skills CoC7 ticked for development during the run unticked, every chat message the run made deleted (the last line checks the count). A step that changes a setting, an actor, the Player's character or makes an encounter puts it back itself in a `finally`.
- **Keep it in line with the code:** a change adds or updates steps for what it changed (`tools/e2e/steps/<area>.mjs`), and a renamed class or attribute is fixed once in `tools/e2e/selectors.mjs`.

What the e2e check has shown about Foundry and CoC7:

- Foundry v14's join page can show a user list (`select[name="userId"]`) or a name field (`input[name="username"]`); the e2e login handles both.
- A request to a player is a whisper whose content holds CoC7's roll link (`@coc7.check[…]`, drawn as a button by CoC7); a roll CoC7 makes itself (an NPC rolled for the Keeper) and the opposed card carry `flags.CoC7`; the opposed card's content holds `coc7-group-actor-roll` (CoC7 8.15).
- A player can control only tokens they own: `Token#control` on another token does nothing, so "the same tokens" for the Player means those they own.
- The demo world's Player has no assigned character (`User#character` null), so a player's panel shows nothing until one is assigned; the player steps assign Helen and put it back.
- Foundry maps `CONFIG.Dice.randomUniform()` to a face as `ceil((1 − u) × faces)` (`DiceTerm#mapRandomFace`): a page that wants low rolls sets it to return 0.95, not 0.05.
- Unit tests with fake buttons can't show CoC7 reading `event.currentTarget` after an `await` (see "Clicking a card button from code"); only the e2e check did.
- Foundry's Tab and Escape over the canvas are its own keys (see "Panel layer"): a step that presses either must expect that.

## CoC7 integration

Researched from CoC7 **8.15** as installed in Foundry's `Data/systems/CoC7/`. The Foundry side was read from the installed build 368 client source (`%LOCALAPPDATA%\Programs\Foundry Virtual Tabletop\resources\app\client\`), which is more exact for this build than the online docs. Everything here is **(assumed)** unless marked confirmed or listed as confirmed in the registry.

**Reading CoC7's source.** CoC7's `system.js` is one minified bundle, but its last line is a source map that holds all 196 original files. File names below (`apps/link.js`, …) are those original paths under `coc7/`. To recover them into a scratch folder outside the repository:

```
node -e "const fs=require('fs'),p=require('path');const[src,out]=process.argv.slice(1);const m=JSON.parse(Buffer.from(fs.readFileSync(src,'utf8').match(/base64,([A-Za-z0-9+\/=]+)\s*$/)[1],'base64'));m.sources.forEach((f,i)=>{const o=p.join(out,f.replace(/^webpack:\/\/[^\/]*\//,'').replace(/\.\.\//g,''));fs.mkdirSync(p.dirname(o),{recursive:true});fs.writeFileSync(o,m.sourcesContent[i]||'')})" <Foundry data>/systems/CoC7/system.js <scratch-folder>
```

**Reading CoC7's compendiums.** `systems/CoC7/packs/<pack>/` are LevelDB folders; the records sit in the `.ldb` table, Snappy-compressed, so they can't be grepped. A throwaway dependency-free reader (SSTable footer → index block → data blocks, Snappy decoded by hand) written to a scratch folder, never to the repository, reads them. With Foundry closed, `fvtt package unpack` (the Foundry CLI) would do the same but is not installed.

## CoC7 links and options

### Link syntax

Parsed by `CoC7Link._createLink`, run on click by `CoC7Link._onLinkClick` → `_onLinkActorClick` (`apps/link.js`). Options are `key:value` pairs separated by commas; a bare key (`blind`, `pushing`, `combat`) means true.

| Option | For | Values | Notes |
| --- | --- | --- | --- |
| `subtype` | check | `characteristic`, `attribute`, `skill`, `combinedall`, `combinedany`, `opposed` (also `char`, `charac`, `attrib`, …) | Picks the actor method or card |
| `name` | check, item | characteristic key `str con siz dex app int pow edu`; attribute key `lck san`; skill name as on the sheet (`Fighting (Brawl)`) or CoC ID (`i.skill.spot-hidden`); weapon name | `idea`/`know` are **not** accepted (see Gap 6) |
| `rolls` | combined, opposed | roll strings joined by `&&` (see "Cards") | Not offered in CoC7's dialog, but parsed |
| `difficulty` | check, sanloss | `?` or `-1` hidden; `+` or `2` hard; `++` or `3` extreme; `+++` or `4` critical; anything else (`0`, `1`, empty) regular | `CoC7Utilities.convertDifficulty`. Omitted: CoC7's world setting `defaultCheckDifficulty`. Always send it. **Sanloss takes numbers only**: the Sanity card sets it with `parseInt` and throws "Difficult level is invalid" on `+` / `++` (`CoC7DicePool#difficulty` setter), so CoC7's own changelog example `difficulty:++` fails in 8.15. Rollbox sends numbers everywhere. |
| `poolModifier` | check, sanloss | `-2` … `2` | Penalty or bonus dice; clamped to ±2. CoC7 picks the link's text by whether the option is **present** (`CoC7.LinkCheckDiffModif`, …), so `poolModifier:0` reads "[hard] Spot Hidden check(0)" (seen at the table). Check links leave it out with no dice; a missing one rolls as 0 (`CoC7RollNormalize`: `options.poolModifier ?? 0`). Sanity links keep `poolModifier:0`: `CoC7SanCheckCard.create` sets the difficulty only when `poolModifier` is defined. |
| `blind` | check | bare `blind`, or `blind:false` | Parsed for sanloss and item too, but ignored there. Always send `blind` or `blind:false` (see "v14 chat modes"). `blind:false` reaches the actor methods as the string `"false"`, which they read as false (`options.blind === 'false' ? false : !!options.blind`). |
| `pushing` | check | bare | Only changes the link's tooltip and default text ("… check - pushing"). The roll is not marked pushed (Gap 3). |
| `combat` | check | bare | Combined/opposed card in combat mode. Rollbox sets it only for a maneuver's opposed card (`combat: true`, through `_onLinkActorClick`). |
| `icon` | all | Font Awesome classes | Optional |
| `sanMin`, `sanMax`, `sanReason` | sanloss | loss on success, loss on failure (number or dice), source name | See "Cards: Sanity" for what `sanReason` does |
| `{label}` | all | the text shown on the link | Without it the tooltip text is shown |

- Old keys `modifier` and `type` still work but log a deprecation warning (until v15). Don't use them.
- Characters that break the syntax: `,` `:` `[` `]` inside option values, `}` inside the label. CoC7 inserts the label into HTML without escaping it (`<span>${name}</span>`), after Foundry has decoded the message's entities, so Rollbox strips `[ ] { } < >` from labels and escapes them with `escapeHtml()`. Option values and roll keys that hold those characters are refused, not altered, so CoC7 never gets a different skill's name.
- Then CoC7's roll dialog (`CoC7RollDialog`) opens, prefilled with the link's difficulty and dice. The player can change difficulty, dice and card type before rolling (Gap 9). Shift-click skips the dialog.
- Hidden difficulty works on the card: the roll is made with difficulty "unknown", and the Keeper sets the difficulty afterwards with Keeper-only buttons on the result card (`roll-result.hbs`).

### Who a click rolls for

- On click, a **Keeper** runs the request once **per selected token** (or for the speaker's actor, or posts the link if neither); Ctrl-click opens the Create link dialog. Rollbox leaves this alone, its own request messages included: it never intercepts or changes CoC7's click handling.
- A **player** gets CoC7's actor picker (`CoC7ActorPickerDialog.create`, "Pick who to roll as"), which picks automatically when they own exactly one character and otherwise preselects their assigned character. The link is not tied to an actor. Shift-click skips CoC7's roll dialog, not the picker.
- **How the click reaches CoC7 on v14** (Foundry build 368 `applications/ux/text-editor.mjs`, `applications/elements/enriched-content.mjs`): `CoC7Link.init` registers its enricher with an `id` and `onRender`. Foundry wraps such an enricher's result in an `<enriched-content enricher="coc7-enricher">` element, whose `connectedCallback` calls `onRender(element)`; CoC7's `onRenderEnricher` adds a bubbling `click` listener there that calls `_onLinkClick(event)`. (The `document.body` listener in `CoC7Link.init` is only for v12.)

### Creating request links

Build the link text (format above) and post it with `ChatMessage.create`, as CoC7's Create link tool does (`CoC7ContentLinkDialog.createLink` → `CoC7Link.fromDropData` → `_createDocumentLink`, `apps/content-link-dialog.js`). Writing the text ourselves avoids `_createDocumentLink`. Rollbox copies no links: a Keeper who wants one uses CoC7's own Create link tool.

```
Characteristic   @coc7.check[subtype:characteristic,name:str,difficulty:+,poolModifier:-1,blind:false]{STR}
Attribute        @coc7.check[subtype:attribute,name:lck,difficulty:1,blind:false]{Luck}
Skill, hidden    @coc7.check[subtype:skill,name:Spot Hidden,difficulty:?,poolModifier:1,blind]{Notice the cultist's hidden knife}
Pushing marker   @coc7.check[subtype:skill,name:Climb,difficulty:1,blind:false,pushing]{Climb}
Sanity           @coc7.sanloss[sanMin:1,sanMax:1D6,sanReason:Ghoul,difficulty:1,poolModifier:0]{The ghoul}
Item             @coc7.item[name:Shotgun]{Shotgun}
Combined, all    @coc7.check[subtype:combinedall,rolls:skill#Spot Hidden#1&&skill#Listen#1]{Spot Hidden and Listen}
Combined, any    @coc7.check[subtype:combinedany,rolls:skill#Spot Hidden#1&&skill#Listen#1]{Spot Hidden or Listen}
Opposed          @coc7.check[subtype:opposed,rolls:Actor.aaa#skill#Stealth#+1&&Scene.s.Token.t.Actor.bbb#skill#Spot Hidden]{Opposed roll}
```

What each runs (`_onLinkActorClick`): characteristic → `actor.characteristicCheck(name, shiftKey, options)`; attribute → `actor.attributeCheck`; skill → `actor.skillCheck`; all three go through `CoC7RollNormalize.trigger` (`apps/roll-normalize.js`) to a `CoC7Check` card (`apps/check.js`). Sanloss → `CoC7SanCheckCard.create(actorUuid, {sanMax, sanMin, sanReason, difficulty, poolModifier})` (blind dropped). Item → `actor.weaponCheck(options, shiftKey)`, which uses only the weapon name and starts CoC7's melee or ranged **attack** card (Gap 2). Combined and opposed: see "Cards".

Rollbox's link options, each a CoC7 behaviour worked around: no `poolModifier` in check links with no dice, but always `poolModifier:0` in Sanity links; numeric difficulties everywhere; always `blind` or `blind:false`; `#1` in every opposed roll string.

### Whispers

CoC7: `CoC7Link#toWhisperMessage(actors)` (`apps/link.js`) creates one `ChatMessage` per actor with `speaker: {alias: game.user.name}`, `whisper: actor.owners.map(u => u.id)` and content `game.i18n.format("CoC7.MessageTargetCheckRequested", {name: actor.name, check: link})` ("Your keeper has requested {name} make a {check} roll."). The "Whisper to selected tokens" button (`CoC7ContentLinkDialog.#onSubmit`) first drops actors without owners: `canvas.tokens.controlled.filter(t => t.actor.owners.length)`. `actor.owners` is every non-GM user with OWNER permission.

Rollbox does the same with public calls: `ChatMessage.create` per character with the owners' ids, and CoC7's own strings via `game.i18n.format` so players see the wording they know. **Never create the message with an empty `whisper` list**: Foundry makes it public. Rollbox posts no public requests (no Send to chat).

### v14 chat modes

v14 renamed roll modes: the setting is `core.messageMode` with modes `public`, `gm`, `blind`, `self`, `ic`. `core.rollMode` is now a deprecated shim (until v16) that returns the old names (`publicroll`, `blindroll`, …). CoC7 8.15 builds its mode constants from the new names but reads `core.rollMode` first, so wherever it falls back to "the roller's chat mode" it compares old names with new ones. For a check without `blind`, Foundry's shim still applies the chat mode, but CoC7's blind-card buttons don't appear; the Sanity card's GM or blind whisper never happens. Each first roll also logs one deprecation warning. Rule: Rollbox always sends `blind` or `blind:false`. Rollbox never reads `core.rollMode` or calls `ChatMessage.applyRollMode`; the v14 deprecation warnings in the maintainer's console come from CoC7 (`roll-normalize.js`, `check.js`).

### Labels

- **The Keeper's text**: the check as CoC7 names it, " · ", then the text, built in `roll-requests/` (`keeperLabel`) for requests: "Hard Spot Hidden · notice the knife"; combined "Spot Hidden + Listen · notice the knife". The Check flyout's Sanity tab builds "Sanity check · <cause>" itself, since only it knows whether the cause was typed; with no cause it sends "Sanity (1/1D6)", so players don't see CoC7's own "[regular] SAN loss(0) (1/1D6)" (the "(0)" is the `poolModifier:0` the link must keep). CoC7 puts the label into its request sentence unchanged ("make a Hard Spot Hidden · notice the knife roll").
- Idea and Know are INT and EDU checks with the Keeper's own label ("INT · Idea"); a weapon "Firearms (Handgun) with the .38 Revolver"; an improvised weapon "Fighting (Brawl) with Candlestick". Labels stay short because CoC7's link button doesn't wrap.

## Cards

### Combined (all or any)

By link: `subtype:combinedall` or `combinedany` with `rolls`. On click, `CoC7ChatCombinedMessage.createGroupMessage({defaultActor, isCombat, rollRequisites: rolls.split("&&"), type})` (`apps/chat-combined-message.js`). For a player it asks the Keeper's client to create the card through CoC7's socket (`CoC7SystemSocket.requestKeeperAction`), so a Keeper must be logged in. The card shows a Roll button to the owner; one roll is compared with every check (`rollForActor`) and the card shows success or failure for All or Any (`getTemplateData`).

Roll strings (`parseRolls`): `[actorUuid#]type#key[#modifier…]`
- `type`: `characteristic`, `attribute`, `skill` or `item`; `key` as `name` in the link table.
- Modifiers, each after `#`: `+1`/`-2` dice; one digit for difficulty `1`–`4`, where **`0` means hidden** (not `?`); `p` tags the roll "Pushing" and removes its Push button.
- Actor prefix optional: without it, the clicker's actor. All rolls on one combined card must be the same actor.
- No blind: the combined card is always public (Gap 5). Missing skills are added to the sheet (`addActorRoll`, see "Skills the actor doesn't have").
- Several characters: one whispered link per character, each without an actor prefix.

### Opposed

Roll strings as for combined, each with its actor's uuid, joined by `&&`. Created by `CoC7ChatOpposedMessage.createGroupMessage({defaultActor, isCombat, rollRequisites})` (`apps/chat-opposed-message.js`), which always makes a **new** card.

From code, the only route that makes exactly one card:

```js
CONFIG.CoC7Link.documentClass._onLinkActorClick(actorA, {
  check: "check", subtype: "opposed", combat: false,
  rolls: `${actorA.uuid}#skill#Stealth#+1&&${actorB.uuid}#characteristic#pow`
});
```

`actorA` must be a real actor (CoC7 reads `actor.uuid` before parsing). It's an internal (underscore) method, so it's guarded and in the registry. Not `game.CoC7.macros.linkMacro` and not a link the Keeper clicks: the Keeper has tokens selected, so `_onLinkClick` would make one card per token (so an opposed roll can't be copied as a link). Not `actor.runRoll({cardType: "C/OP"})`: it joins any open opposed card under a day old, then throws.

- **Difficulty:** opposed rolls have no difficulty to choose (p. 92), but **always send `#1` (Regular)** in each roll string: without a digit `parseRolls` uses the world's `defaultCheckDifficulty`, which can be "unknown" (hidden).
- **Missing skills:** making the card adds any missing skill to that side's sheet (`addActor` → `getItemOrAdd`, on the Keeper's client, NPCs included; the maintainer accepted this); a skill CoC7 can't find stops the card with "Unknown skill", so Rollbox checks first (`coc7FindsSkill`) and tells the Keeper instead.
- **Start rolls:** sides can be removed until the Keeper clicks **Start rolls** (`rollNoPlayers`, Keeper-only). That click locks the card and rolls every side whose owners aren't online: each side gets `playerOwnersOnline` when it is added to the card (non-GM users that are `active` and `actor.canUserModify(user, "update")`), and `rollNoPlayers` rolls every side whose list is empty. The list is taken when the card is made, so a player who logs in afterwards still has their side rolled by Start rolls (seen at the table for an offline player). Only then can players roll their side (`rollActor`). Rollbox clicks Start rolls on the Keeper's client (Gap 8, B; "Clicking a card button from code") and tells the Keeper ahead which side it rolls ("Keeper rolls (NPC)", "Keeper rolls (player offline)") from `actor.owners` and `User#active`.
- **Comparing and ties:** `getTemplateData` compares: higher success level wins; equal levels set `isTie` and show "Tie" with no winner outside combat (Gap 7); Advantage buttons only appear in combat. CoC7's house rule `opposedRollTieBreaker` only changes the order of sides on combat cards. So the Opposed flyout shows the Keeper which side has the higher value (p. 91), comparing the two values only; CoC7 still compares the rolls. The card offers no Luck and no Push.
- **Roles: a card always has an attacker and a defender.** The first roll string is CoC7's attacker, the second its defender; `_onLinkActorClick` is called with the first side's actor, and Swap sides only reverses the two. The maintainer asked for cards with both sides at no role; not possible through `_onLinkActorClick` (or any public route): `parseRolls` reads `#a` / `#d` from a roll string, but `addActor` then resets every side to `participant.none` (line 477 of the recovered file); `newGroupMessage` (lines 200–217) makes the last side with no role defender and the rest attacker when the card has exactly two sides. `getTemplateData` sets `allRollsAssigned` only with exactly one attacker, one defender and no side without a role (lines 680–681), and compares only then; otherwise the template shows a disabled "An opposed card needs an attacker and defender" (`CoC7.ErrorOpposedRollsMissingAttackerDefender`) in place of Start rolls (`opposed-roll.hbs` lines 50–51). A one-side card joined later (`joinGroupMessage`, which keeps both at none) would need `runRoll` with `C/OP`, which joins any open card under a day old and then throws, and would still not compare. So Rollbox keeps Swap sides and its Attacker/Defender tags. Outside combat the roles don't change who wins. The card's Keeper-only role button doesn't cycle to none either: clicking the attacker makes it defender (and the other attacker); clicking any other side makes it attacker (lines 253–266).
- **One side only:** Shift + Right with one character opens Opposed with that side waiting instead of making a card: Rollbox can't finish a one-sided card made through `_onLinkActorClick` itself (joining from code needs `runRoll` `C/OP`, above); only the Keeper can, by hand (next point). The panel sends a Shift + Left on a characteristic to Opposed while `opposedWaiting()` is true.
- **A side left for the Keeper** (a player's Opposed, traced in CoC7 8.15 and seen in e2e): a card made through `_onLinkActorClick` with one roll string is an open card with that side and no role ("An opposed card needs an attacker and defender"). The Keeper finishes it with CoC7's own UI: a right click on a check on the opponent's sheet (`_onOpposedRoll`, bound only while the sheet is locked, on `.characteristic-name.rollable`, `.skill-name.rollable`, `.attribute-name.rollable`, `.weapon-name.rollable`) opens CoC7's roll dialog with **Opposed roll card**; its Roll goes to `CoC7ChatOpposedMessage.joinGroupMessage`, which on a GM's client adds the roll to the **newest** open opposed card (`cardOpen`, not rolling, under a day old; else it makes a new card). The joined side has no role either. The role button (`data-action="participant"`, Keeper-only) makes a side with no role attacker; clicking the attacker makes it defender and every other side attacker; so two clicks on the joined side give the first side Attacker and it Defender, and Start rolls appears. Rollbox presses them: the active Keeper's client watches the card it made (`card-buttons.js` `setRolesWhenJoined`: CoC7's opposed card by this user, newer than the request, the player's side alone) and, at each render once a second side is on it, presses the joined side's role button once, until the player's side reads `A` and the joined side `D` (`flags.CoC7.load.actorRolls[uuid].participant`; at most four presses, then the Keeper is told). The button is bound by CoC7's own card listeners, so a press waits for them (`pressWhenReady`). Start rolls stays the Keeper's. The watch ends with the roles set, the card rolled or closed, deleted, or after a day (CoC7's own join window).
- **No card:** `send()`'s result names why in `skipped` (a side's skill CoC7 can't find, a name that can't go in a roll string, CoC7's link handler missing or throwing), and the view shows it.

### Sanity

`CoC7SanCheckCard` (`apps/san-check-card.js`, `templates/chat/san-check.hbs`): the player rolls Sanity on the card. On a failure the Keeper first clicks "Perform involuntary action"; the loss is rolled on the card (`rollSanLoss`) and applied only when the Keeper clicks **Apply: N** (`sanLossApplied` → `applySanLoss` → `actor.loseSan`). Both buttons are Keeper-only (`keeper-only-block`, removed for players by `hooks/render-chat-message-html.js`). The INT roll, bouts of madness, indefinite insanity and Cthulhu Mythos all follow on the same card. (Confirmed at the table: SAN 60 → 54 only after Apply, then CoC7's bout-of-madness and Mythos options, and the creature recorded.)

- `sanReason` is a record per actor (`maxLossToSanReason`): later losses to the same source are capped by what was already lost to it. Use the creature or source name (e.g. "Ghoul"), not free text. The players see the link's `{label}`.
- **Both losses go to Foundry's `Roll`.** `getTemplateData` evaluates `new Roll(sanMax).evaluateSync({ maximize: true })` every time the card is drawn (`maxRollableSanLoss`); the loss is rolled with `new Roll(sanLossFormula)`; on a fumbled Sanity roll the loss is the maximum of `sanMax`. A loss that is only a number is used as that number, not rolled. So a malformed loss breaks the card, not just the roll: Rollbox accepts only whole numbers and `[N]D<faces>` terms joined by `+` or `-` (`sanityLoss`, one rule for the flyout and the request).
- **Creature cap:** with `sanReason` set, a creature the character has already lost the maximum to (`actor.maxLossToSanReason(sanReason, sanMax) === 0`) needs no loss roll: the card marks the character immune to it. A rolled loss above the remaining cap is cut to it ("limited loss to creature").
- **A loss of `0`** (e.g. the success side of 0/1D6) needs no loss roll on the card.
- The card's Sanity roll button is `[data-action="rollSanCheck"]` in an `owner-and-keeper-block` (the owner or the Keeper can click it); the message flag is `flags.CoC7.load.as === "CoC7SanCheckCard"` with `actorUuid`. Rollbox clicks it for NPCs (see "Rolling NPCs").
- Blind: the link parses `blind` but doesn't pass it to the card; the card follows the clicker's chat mode, which on v14 never matches ("v14 chat modes"). Gap 4.
- CoC7 never offers Push or Luck on a Sanity roll.

### Rollbox's own card: Assist

Nothing new from CoC7. Each roller gets an ordinary characteristic check (`checkRequest` with `str` or `siz`) through `roll-requests/`, so the links, whispers and NPC rolls are exactly the Check flyout's. The Assist card is Rollbox's own public `ChatMessage` (HTML built with `escapeHtml`, `speaker: { alias: <the Keeper's name> }`, no `whisper`), as the request messages are made. Rollbox doesn't read the rolls back (reading CoC7 results was researched, not planned: `game.CoC7.messageResults()` reads a card's result, and CoC7 8.15 reports the first roll after a push).

### Clicking a card button from code

CoC7 attaches each card's listeners in its async `renderChatMessageHTML` handler, after awaiting `CoC7Utilities.canModifyActor` (`hooks/render-chat-message-html.js`). A click in the same tick as Rollbox's own render hook lands before the listeners and does nothing. Rollbox waits 250 ms and retries up to eight times (`card-buttons.js`). (Confirmed for Start rolls.)

- **CoC7's card handlers read `event.currentTarget` after an `await`** (`_onClickEvent`: `const check = await …loadFromMessage(message), set = event.currentTarget.dataset.set`). A person's click resumes them while the event is still dispatching; a click made by a script (`element.click()`, `dispatchEvent`) has finished dispatching first, the browser has cleared `currentTarget`, and CoC7 throws "reading 'dataset'" of null, so the toggle silently stays off. Rollbox presses CoC7's controls with `roll-requests` `pressControl`, an event whose own `currentTarget` property is the control.
- `clickCardButton` returns a function that ends the watch quietly; Rollbox calls it when `_onLinkActorClick` throws, so the Keeper isn't told 15 seconds later to click a card that never came.

### Rules CoC7 already enforces on its cards

- No Push and no Luck on Sanity rolls; no Luck on Luck rolls; no Luck after a push or on a fumble (`CoC7DicePool#availableButtons`, `apps/dice-pool.js`).
- CoC7 **does** offer Push on a failed Luck roll, which p. 84 forbids. Rollbox can't change CoC7's card; the Keeper refuses at the table.
- The opposed card offers no Luck and no Push.

## Rolling NPCs

On the Keeper's client: `actor.skillCheck(name, true, {difficulty, poolModifier, blind: true})`, or `characteristicCheck(key, true, …)` / `attributeCheck(key, true, …)`. `true` is fastForward (no dialog). `blind: true` puts the card in CoC7's blind mode: whispered to GMs only (`CoC7Check#getChatData`), and the Keeper sees the full result plus reveal and force buttons. NPCs have no player owner, so the roll is made at once. (Confirmed: a Hard Spot Hidden on two NPCs gave Keeper-only blind cards, no dialog.)

`actor.runRoll({characteristic | attribute | skillName, difficulty, poolModifier, isBlind: true, fastForward: true})` does the same and returns `{result, successLevel, passed, …}`. `difficulty` here is a number (`1`–`4`, `-1` hidden), not `+`. It is the only way to roll Idea or Know (`characteristic: "idea"` or `"know"`) or a raw value (`rollType: "R/MA", threshold: 20`). It throws for opposed, combined and Sanity card types.
- Idea and Know ignore `poolModifier`: their dice are `poolModifierIdea` / `poolModifierKnow` (`normalizeRequest`, which then falls back to the actor's `system.config.idea.bonusDice`). Rollbox doesn't roll them this way: they are INT and EDU checks (Gap 6).
- A raw-value card's flavour is "(20%) - Regular difficulty", with no skill name, and `runRoll` passes no custom flavour, so Rollbox whispers the Keeper a note naming the skill.
- A check with 0 dice picks up the skill's, characteristic's or attribute's own `bonusDice` in `normalizeRequest`.

Standby cards: when the Keeper triggers a check on an actor that has a player owner and CoC7's world setting `stanbyGMRolls` (CoC7's spelling) is on (default true), CoC7 posts a card with a Roll button only the owner and the Keeper can use (`roll-standby.hbs`). The actor check methods allow this; `runRoll` prevents it unless given `preventStandby: false`.

Rollbox's NPC rules (`roll-requests/keeper-rolls.js`; settled with the maintainer, where CoC7 can't do what the design says):
- **Missing skill:** a raw roll (`R/MA`) at Rollbox's base value, nothing added to the sheet (Gap 1, C).
- **Combined check:** one private raw roll at the highest value for "Any one" (p. 203) or the lowest for "All of them", which passes or fails exactly when the combined card would; a note to the Keeper names the checks. CoC7's combined card is always public and adds missing skills, so it isn't used for NPCs.
- **Idea and Know** are sent as INT/EDU checks with a label (Gap 6), so an NPC gets an ordinary private INT or EDU check, not CoC7's own Idea or Know card.
- **Labels:** CoC7's private NPC card (and the raw `R/MA` card) shows no link label, so Rollbox puts the label in its Keeper note ("Guard: Hard Spot Hidden · notice the knife").
- **Order:** how to roll is decided first, then the Keeper's note is posted and CoC7 is called once, so the note always comes just before CoC7's card.
- **Sanity:** CoC7's Sanity card made on the Keeper's side (`_onLinkActorClick` with `check: "sanloss"`), and Rollbox clicks its Sanity roll (`rollSanCheck`). The card is public (Gap 4).
- **Opposed:** the NPC side is rolled by Start rolls (see "Cards: opposed").

## Skills and weapons

### Skill-name matching is skill-values'

`scripts/skill-values/` is the only code that matches skill names (`comparable`, `isCocid`, `tableSkill`, `groupBase`, `sheetSkill`; for the flyouts and roll-requests also `findSkillRow`, a skill's row by CoC ID then name, `sameSkill`, whether two references are one skill, `skillKey`, a flyout row's key, and `tableBaseFor`, a table skill's base for one actor) and the only reader of `base-skills.js`, so the flyouts list a skill and `roll-requests/` sends it by one rule. `checkChoices(actor, { sanity })` gives the rows of the Check flyout's and the Opposed flyout's three tabs, so both list the same checks in the same order. Rollbox compares whole names (no accents, lower case, single spaces) and CoC IDs itself; it doesn't call CoC7's `actor.getSkillByName` (which matches the CoC ID or compares only `skillName`, "Handgun", ignoring accents).

The own-language rule: a sheet's own language (CoC7's `system.properties.own`, often renamed "Language (English)") is listed as Language (Own)'s row by the flyouts, and a request for Language (Own) by its CoC ID (`i.skill.language-own`) finds that item; a request by name doesn't take the flag, because CoC7 finds a renamed own language only by CoC ID.

### Skills the actor doesn't have

CoC7 8.15 does **not** roll a generic 1D100. `actor.skillCheck` calls `actor.getItemOrAdd(name, "skill")` (`models/actor/document-class.js`): it looks on the actor (by name, ignoring accents, or by CoC ID); if the skill isn't there, it looks in world items and then every Item compendium (filtered by era) and **adds the skill to the actor's sheet**, with the notice "This skill {name} has been added at {percent}%". If it finds nothing, nothing happens. The combined and opposed cards do the same (`addActorRoll`, `addActor`). It runs on the clicker's client: the player's for their character, the Keeper's for NPCs. The added value is CoC7's skill item's base, not Rollbox's table.

Rolling a value without adding anything: `actor.runRoll({rollType: "R/MA", threshold: 20, difficulty, poolModifier, isBlind, fastForward: true})` (`CoC7Check#rollManual`). The card shows the actor and "(20%) - Regular difficulty", but no skill name. Keeper side only; there is no link form. See Gap 1.

- **Lookup order** (`getItemOrAdd`): a CoC ID (`i.skill.…`) → the actor's item with that CoC ID, else `game.CoC7.cocid.fromCoCIDBest({cocid})`, used only when it returns exactly one item; a UUID → that item on the actor (`items.get`); a name → `actor.getItemByName`, then world items, then each Item compendium's index (`pack.getIndex()`; CoC7 adds `system.skillName` and the CoC ID flag to the index fields), skipping skills whose `flags.CoC7.cocidFlag.eras` doesn't include the world era.
- **Names compare only the part in brackets.** `getItemByName` and `getSkillByName` compare `system.skillName` ("Handgun" for "Firearms (Handgun)", from `guessNameParts`), without accents or case. A sheet's renamed own language ("Language (English)") isn't found as "Language (Own)" by name, only by CoC ID.
- **If CoC7 finds nothing, a player's click does nothing**: `skillCheck` returns silently. So a request for a typed skill no compendium has (e.g. "Pilot (Boat)": CoC7's compendium has only "Pilot (Any)") is dead. Rollbox checks first with the same lookups and tells the Keeper instead (`docs/roll-requests.md`, `coc7FindsSkill`).
- Requesting a sheet skill by a CoC ID the sheet item doesn't carry would make CoC7 add a duplicate from the compendium; Rollbox requests on-sheet skills by the item's own CoC ID or its name, and NPC rolls by the item's uuid.

### A weapon's skill

Read in CoC7 8.15 (`models/item/weapon-system.js`, `models/actor/document-class.js`, `apps/chat-combat-ranged.js`, `apps/chat-opposed-message.js`, `templates/items/weapon-header.hbs`, `apps/chat-combat-melee.js`).
- **Stored skill:** `system.skill.main` and `system.skill.alternativ` (CoC7's spelling), each `{ name, id }`; `id` is the skill item's id on the actor's sheet. On compendium weapons the `name` can be a CoC ID (`i.skill.throw`, set by CoC7's `coc-id-batch.js`); Rollbox treats a name starting `i.skill.` as a CoC ID, so labels use the skill's name. When CoC7 adds a weapon to an actor through `getItemOrAdd` / `getItemAdding`, it resolves each name to a sheet skill (adding the skill if needed) and stores its id and name. CoC7's own rolls read only the id (`skillMain`, `skillAlternative`, `isSkillSet`).
- **`system.usesAlternativeSkill`** is true when the weapon has the automatic (`auto`), burst (`brst`) or thrown (`thrown`) property, whatever the shot.
- **Which skill CoC7 uses:** its opposed and combined cards take `skill[usesAlternativeSkill ? "alternativ" : "main"].id` and fail with "Unknown skill" when that id is empty. Its ranged attack card uses the alternative only for burst or full-auto fire and the main skill for single shots.
- **Two skills:** CoC7's weapon sheet shows the alternative-skill field only when the weapon is automatic, burst or thrown (`usesAlternateSkill`), and CoC7's own lists of a weapon's skills (`getWeaponSkills`, the melee card) add the alternative only when its id is set. Rollbox offers two rows only when `usesAlternativeSkill` is true and the two stored skills differ; `weaponRequest({ skill: "main" | "alternative" })` picks one. Without `skill`, the cards' rule applies.
- **Fallback:** CoC7's `skillAlternative` getter returns the main skill when the alternative's id is empty, and so does Rollbox's `weaponSkill` (alternative id and name both empty). The opposed and combined cards don't fall back; Rollbox never sends a weapon to them.
- **Weapons are sent as labelled skill checks** (Gap 2, A), never `@coc7.item`.
- **Damage:** an improvised weapon's damage goes in the request as a Foundry inline roll `[[/r formula # flavor]]`. `DB` is the character's damage bonus (`system.attribs.db.value`), and `½DB` half of it, filled in the way CoC7's `CoC7Utilities.halfDB` halves it (thrown weapons add half DB). The Other flyout's Item section asks for half when the improvised skill is Throw.

## Combat, statuses and players (CoC7 8.15, Foundry build 370)

Read from CoC7 8.15's built `system.js` and templates and Foundry build 370's client source, and checked by the e2e check; every API here is in the registry, waiting for the maintainer's table check.

### Attack cards and spells
- CoC7's attack card toggles Rollbox may set (Aiming, Reloading, the dice slider, Under cover) are **Keeper-only controls**: only the Keeper's client can set them (CoC7 attaches their listeners for GMs only). A player's toggles go to the Keeper's client through the module socket (below). Rollbox presses them with `pressControl` (see "Clicking a card button from code").
- Each toggle makes CoC7 reload the card from its flags and redraw it (`loadFromMessage` → `updateMessage`), so two changes in a row on the same rendered card lose the first: set one per `renderChatMessageHTML`.
- The attack cards have **no free bonus/penalty toggle**, but a Keeper-only **dice slider** (−2…+2, starting at the weapon's and skill's `bonusDice`); Rollbox's net status dice go there.
- `weaponRoll` posts the card without awaiting it, so `actor.weaponCheck` resolves before the card exists: watch the render hook, don't read its return.
- CoC7 measures ranged distance itself (`distanceBetweenTokens`, centre to centre, yards); melee has no distance check, so the reach greying is Rollbox's only. CoC7's unarmed weapon CoC ID is `i.weapon.brawl`.
- The melee **defender card** (`CoC7ChatCombatMelee`, `participant` 1) is made only after the attacker clicks Roll on their card; its Dodge / No response / Fight back / Maneuver buttons are owner-and-Keeper, and Fight back and Maneuver open CoC7's own dropdown beside the button. CoC7 computes no Build dice for the defender's maneuver; the card's pool slider is Keeper-only.
- The ranged card keeps per-target toggles in `targets[offset].poolKeys`; **Under cover** is the key `cover` (`DICE_POOL_REASONS.cover`), Keeper-only; pressing it also makes that target active.
- **`game.CoC7.messageResults(message)` returns an array**, one public result per roll on the card (`{ messageType, actorUuid, type, key, isRolled, isSuccess, … }`), not one object: read the first rolled entry (`roll-requests` `checkResult`). It is the public way to read a check's outcome without our own success code. A first casting's POW roll reads `{ type: "characteristic", key: "pow" }`.
- **CoC7's `item.system.cast` asks its own "Spell Costs" dialog** (magic points spent on each part of the spell) before it takes the costs and posts its card; it resolves only after Validate. A SAN cost of 5 or more starts CoC7's own bout of madness (an active effect and `system.conditions.tempoInsane`) and adds to `system.attribs.san.dailyLoss`; an e2e step that casts puts all of it back.

- **`actor.weaponCheck({ uuid })` can't take a weapon with no owner.** It reads `weapon.parent.id` first, so a world or compendium item (CoC7's own unarmed weapon, "Punch" in `CoC7.items`, CoC ID `i.weapon.brawl`) throws; only a weapon on another character is copied onto the sheet. Rollbox copies CoC7's unarmed weapon onto the sheet itself (`createEmbeddedDocuments` with its `toObject()`), then attacks with the copy; the copy's skill is found on the character by name, as CoC7's own copy's is. Passing a parentless item straight to CoC7's card classes doesn't work either: the weapon's skill is looked up on the weapon's own character.
- **A weapon whose skill CoC7 can't find has no roll button.** The melee card lists `item.system.skillMain` (and the alternative) as its roll buttons; with `system.skill.main.id` empty or not on the sheet (`system.isSkillSet` false) there is no button, only the Keeper's Automatic Success toggle. CoC7's compendium Punch (`i.weapon.brawl`) stores its skill as `i.skill.brawl` with no id; CoC7's own add (`getItemAdding` / `getItemOrAdd`) resolves it after creating the item, a plain `createEmbeddedDocuments` doesn't, so a plain copy gives a punch with no roll (or an NPC's "automatic success" with no damage).
- **What CoC7's ranged card does itself, when it is made** (`CoC7ChatCombatRanged`): Point blank (`pointBlankRange`, centre to centre, `DEX / 15` yards, i.e. a fifth of DEX in feet), the range band and its difficulty (base, ×2 Hard, ×4 Extreme; shotguns excepted), the target's size (`sizeSmall` at Build −2 or less, `sizeBig` at 4 or more), and later multiple shots (a penalty die on each) and full auto (one per volley). **Never set by CoC7:** Under cover (`cover`), In melee (`inMelee`), fast-moving (`fast`), Reloading, Aiming (all Keeper toggles). A per-target toggle turns over on each press, so press only when it isn't as wanted. The melee attacker card's Outnumbered and Surprised (`togglePoolKey`) are Keeper toggles CoC7 never sets or counts; the melee card has no Build dice.
- **CoC7's Multi. Shots only collects shots** (`CoC7ChatCombatRanged`, `range-initiator.hbs`): with it on, the target's "Shoot Firearms (Handgun)" button (`range-initiator-shoot`) calls `addShotAtCurrentTarget`, which adds one shot with that target's difficulty and dice and rolls nothing ("Shots: 1/3"); the card's bottom **Shoot !!!** (`range-initiator-roll` under `.ranged-shots`) then calls `rollCard`, which rolls every shot, calls `shootAmmunition` per shot and stops at a malfunction. Multi. Shots puts one penalty die on each shot (`#multipleShots && !#fullAuto`); Aiming counts only for the first shot. The add button turns into "Out of shots" at `usesPerRound.max` (unless CoC7's `disregardUsePerRound`) and "Out of ammo" once the shots use every round loaded. The toggle and both Shoot buttons get listeners for the card's owners too (`allowed`), not only the GM; their changes go through `updateMessage`.
- **Toggles must come before the shots:** each shot copies the target's `finalPoolModifier` when it is added, so a Keeper toggle set after a shot is added doesn't reach that shot. Rollbox sets the toggles first, on one client.
- **CoC7's weapon `system.multipleShots`** is true when `usesPerRound.max` is a fixed number above 1 (a `Roll` that is deterministic); `singleShot` likewise for `usesPerRound.normal` above 0.
- **Whip and mace spray are "ranged" in CoC7:** its compendiums' Bullwhip (`i.weapon.bullwhip`, skill `i.skill.fighting-whip`) and Mace Spray (`i.weapon.mace-spray`, Fighting (Brawl)) have `system.properties.rngd` ticked, so CoC7 makes its ranged card for them; their range is in yards as text: `"10/3"` (Keeper items) or `"3"` (CoC7's own en-wiki pack) for the whip, `"6/3"` for mace spray, `"@STR/5"` for thrown spears. CoC7's `Weapon.system.baseRange()` works it out with `new Roll(value, actor.parsedValues())`; the deprecated `Item.baseRange` getter `parseInt`s it first ("10/3" → 10). A weapon CoC7 doesn't mark ranged has its range ignored by the melee card, and imported NPC sheets can hold skill percentages there (a Brawl "45"), so Rollbox reads a range only from a ranged weapon on a Fighting skill.
- **CoC7's compendiums mark shuriken, rocks, dynamite and mace spray ranged with no Thrown tick**, some with a capacity (dynamite 1, mace spray 25): "a firearm" for reloading needs the skill too (not Throw, Fighting, Demolitions). The two weapon compendiums spell some CoC IDs differently (`32-or-7-65mm` / `32-or-7-65-mm`, `25-derringer-1b` / `-1-b`).
- **Reloading:** CoC7's `reload()` sets `ammo` to `bullets`; `addAmmunition()` adds one up to `bullets`; both await the item update, so two awaited `addAmmunition()` calls load two rounds. CoC7 keeps no magazine type.
- **CoC7's melee defender card** (`melee-target.hbs`, `CoC7ChatCombatMelee._onClickEvent`): Dodge (`dodge`) sets the card's item to the defender's `isDodge` skill; No response (`setNoResponse`) sets `isNoResponse`; Fight back (`setFightBack`) and Maneuver (`setManeuvers`) open `CoC7ChatDropdown.makeDropdown`: a `div#dropdown-<message id>` appended to the clicked copy's `.chat-scroll` (it throws outside the chat log), one `setItem` button per non-ranged weapon whose main skill is on the sheet (Fight back) or per skill CoC7 marks `properties.fighting` (Maneuver), A–Z; the dropdown closes only on a mouse leaving it. `setItem` sets the card's item. Each choice is saved (`updateMessage`; a player's goes to a GM through CoC7's socket, which makes the player the message's author) and the card redraws with one roll button, `targetRoll` ("Dodge (30%)", "Knife: Fighting (Brawl) (45%)", "No response"), which rolls (No response rolls nothing) and then makes CoC7's resolution card (`CoC7ChatDamage.createFromCombatMelee`). A defender's answered card sets `responded` (and `isNoResponse` for "no response").
- **Two dodge results after a dodge are both CoC7's:** its defender card shows the Dodge roll, and `createFromCombatMelee` posts its resolution card "Cecil dodged!" (a `CoC7ChatDamage` with no roll). Rollbox posts nothing.
- **The attack card's roll** is `attackerRoll` (melee; one button per skill, the main skill first) or `range-initiator-roll` (ranged, per target; the bottom Shoot after multi-shots). CoC7's Keeper-only Automatic Success (`toggleValue` / `isAutoSuccess`) is a toggle that turns a failed roll into a success, not a roll.
- **A Keeper's attack with an investigator, or a player's own, can be rolled by the client that made the card:** CoC7's `attackerRoll` and `range-initiator-roll` are shown to the card's owner. A player's Keeper-only toggles are set by the Keeper's client, so the player's client waits until each shows set on its render of the card before pressing the roll.
- **CoC7's attack, defender and damage cards carry no speaker** (`CoC7ChatCombatMelee`, `CoC7ChatCombatRanged`, `CoC7ChatDamage` build their chat data without one): Foundry shows the author's name (the Keeper's user name), whether the card came from Rollbox or from CoC7's sheet. A check card (`CoC7Check`, an NPC's check Rollbox has CoC7 roll) carries the character's token as its speaker. Rollbox leaves the attack cards as CoC7 makes them (lane rule).
- **CoC7's casting window** is `CoC7SpellVariablesDialog` (an ApplicationV2 with `HandlebarsApplicationMixin`, classes `coc7 dialog spell-variables`, title "Spell Costs"), opened by `item.system.cast()` only for a spell with a CoC7 cost list (`costList` with a `triggerPrompt`), and awaited inside `cast()`: `cast()` returns once the window is answered. Foundry v14 calls `renderApplicationV2` and `closeApplicationV2` for every ApplicationV2 subclass, so a module can tell when it opens and closes without touching CoC7. The window doesn't say which spell it is for.
- **Spell casting times in the Keeper items compendium** (`cha-coc-fvtt-en-keeperitems.spells`, 128 spells): every spell has a casting time; the forms are "Instantaneous", "N round(s)", "1D3 rounds", "1D6 + 4 rounds", "1 or 2 rounds", "5+ rounds", minutes / hours / days (some "per magic point", "per POW", "Many days", "half a day"), and two dose spells ("2 days per dose, 1 round to apply", "1 round to apply 1 dose"). `flyouts/action/casting-time.js` reads every one of these forms.

### Maneuvers on CoC7's opposed card
- **Maneuver ticked only matters on CoC7's opposed card.** `system.properties.mnvr` is read in one place: the opposed card in combat mode (`CoC7ChatOpposedMessage`, roll type `item`), which then says "<name> maneuver was successful". `actor.weaponCheck` / `weaponRoll` (what CoC7's sheet does when a weapon is clicked) always makes the plain melee attack card for a non-ranged weapon, Maneuver ticked or not, and the card reads a win as a hit and offers damage. On the melee card a maneuver is a defender's response only (its fighting skill); an attacker's card from a skill item has no roll button. So Rollbox runs an attacker's maneuvers on the opposed card.
- **CoC7's maneuver card is its opposed card in combat mode** (`CoC7ChatOpposedMessage`, `isCombat`). `_onLinkActorClick(actor, { check: "check", subtype: "opposed", combat: true, rolls })` calls `createGroupMessage({ defaultActor, isCombat: true, rollRequisites })`; on a GM's client `newGroupMessage` makes it (on a player's, CoC7 asks a GM through its own socket). Its roll format takes a weapon: `<actorUuid>#item#<name or item uuid>#<±dice>#<difficulty>`; `addActor` finds it with `getItemOrAdd(key, "weapon")` (a name, a CoC ID or an item uuid), rolls the weapon's skill (`usesAlternativeSkill` picks main or alternative; no skill id: "Unknown skill" and no card) and keeps `isManeuver` from `system.properties.mnvr`. By hand from the sheet only skills, characteristics and attributes reach the card (a right-clicked weapon fails with "Roll Type is not a valid formula", a CoC7 bug).
- **Sides:** `addActor` resets every side to no role (`#a` / `#d` in a roll string are read and then dropped); with exactly two sides `newGroupMessage` makes the last one defender and the first attacker. The card compares only with one attacker and one defender; until then Start Rolls is a disabled "An opposed card needs an attacker and defender". The Keeper's portrait button (`data-action="participant"`) makes a side attacker, or, on the attacker, defender and the rest attacker.
- **Start Rolls** (`rollNoPlayers`, Keeper-only) rolls every side whose `playerOwnersOnline` is empty (taken when the card is loaded: non-GM, active, may update the actor); each player rolls their own row (`rollActor`, the listener attached for the actor's owners), and their update goes to a GM through CoC7's socket.
- **Endings** (`getTemplateData`, combat mode): the higher success level wins; "<name> maneuver was successful." (`CoC7.ManeuverSuccess`) when the winner's row is a weapon with Maneuver on, "<name> dodged!" (`DodgeSuccess`) for a winning defender on Dodge, else "<name> landed a blow." (`AttackSuccess`); no winner "Both side failed." (`NoWinner`), also shown on a tie until an Advantage is chosen. A tie where every side succeeded sets `canAdvantage`: the Keeper-only **Advantage: Attacker / Advantage: Defender** (`[data-action="setValue"][data-set="advantage"][data-value="A"|"D"]`) picks the winner. A weapon winner gets **Roll damage** (`winnerRollsDamage`, the weapon found by `getItemByName(key)`) in place of Close card, also after a maneuver.
- **The opposed card's rows:** each `.coc7-group-actor-roll`, the winner's with `won`, the attacker's with `attacker`. A row's Roll dice (`rollActor`, `data-actor-uuid`) shows only once `isRolling` (after Start Rolls).
- **The opposed card's Roll damage** (`rollDamage`) calls `CoC7ChatDamage.createFromActors({ attacker: winner, weapon: winner.getItemByName(key, "weapon"), isCritical, target: loser })` (critical when the winner beat Extreme) and closes the card; it is offered only when the winner's row is a weapon (`winnerRollsDamage`). The damage card it makes doesn't roll: it shows its own "Roll damage: 1D3+DB" button. **`CoC7ChatDamage` isn't exposed** (not on `game.CoC7`, not on `CONFIG`; the bundle exports nothing), so another module can't call `createFromActors`. The character sheet's damage roll (`_onWeaponDamage`, `data-action="weapon-damage"`) calls `CoC7ChatDamage.createFromWeapon({ attackerUuid, weaponUuid, damageRange })`: the same card for the weapon, not critical, with no target ("Cecil deals 1D3+DB with Punch" instead of "<target> takes …"; no armour line). Its handler reads only `event.currentTarget.closest(".item").dataset.itemUuid` and `dataset.range`.
- **Build is only shown:** every combat-mode row gets the tag "Maneuver (Build: N)"; CoC7 applies no Build dice. Rollbox puts the p. 105 penalty dice in the maneuver side's roll string.
- **CoC7's Maneuver toggle on the weapon sheet** is `system.toggleProperty("properties", "mnvr")` → `prepareToggleUpdate` → `item.update({ "system.properties.mnvr": !value })` (not awaited by CoC7). Rollbox makes the same update and awaits it.
- **CoC7 reads a weapon's Maneuver once, when it adds the row to its opposed card** (`CoC7ChatOpposedMessage#addActor`, roll type `item`: `isManeuver = item.system.properties.mnvr`), and keeps it in the card's flags (`flags.CoC7.load.actorRolls[uuid].isManeuver`); every later render (`getTemplateData`) reads the flag, never the weapon. So switching a Punch's Maneuver off before the card is made and back on after leaves the card treating it as an ordinary weapon: a win reads "<name> landed a blow." and offers Roll damage (`winnerRollsDamage`, set for any winning `item` row). Roll damage then finds the weapon by the row's key, its name (`winner.getItemByName(key, "weapon")`), and calls `CoC7ChatDamage.createFromActors` with the loser as the target. This is how a fight back with a Maneuver-on weapon gets CoC7's own Roll damage (DESIGN.md's lane list).
- **`CoC7Link._onLinkActorClick` returns before the opposed card exists:** it calls `CoC7ChatOpposedMessage.createGroupMessage` without awaiting it, and that calls `newGroupMessage` without awaiting it. `addActor` (which reads Maneuver) runs before `ChatMessage.create`, so the card's `createChatMessage` is the first moment the switch can go back on. Rollbox waits for that hook (15 s at most), then switches it back in a `finally`.

### Checks and rolls from code
- **A check with no window:** CoC7's actor checks (`characteristicCheck`, `attributeCheck`, `skillCheck`) take `fastForward` as their second argument; `CoC7RollNormalize.normalizeRequest` turns it into `isShiftKey`, and `trigger` then skips `createRoll` (the `CoC7RollDialog` "select modifier" window) and goes straight to `runRoll`, which rolls and posts the `CoC7Check` card in the roller's roll mode, exactly as a Shift + click on CoC7's sheet. On a player's client there is no standby card (that is GM-only), so the check is rolled. Seen in e2e: no `.bonus-selection` window, the card authored by the player.
- **CoC7's Luck needs a number on the sheet:** `CoC7Check#setThreshold` reads `parseInt(actor.system.attribs.lck.value)` for an attribute check and, when that isn't a number (most creatures, the compendium Deep One), warns "Roll threshold has not been set" (`CoC7.Errors.UnparsableThreshold`) and throws. Rollbox reads the same value through skill-values (`numberOrNull`) and never sends Luck for such a sheet.
- **Foundry's `fromUuidSync`** returns the Actor for an actor uuid and a TokenDocument (`documentName` "Token") for a token uuid; take `.actor` from the latter (`utils.js` `actorFromUuid`).

### Turns, initiative and the encounter
- **CoC7's DEX rolls at combat start are its optional initiative rule.** CoC7 replaces `Combat.prototype.rollInitiative`: with its world setting `initiativeRule` on `optional`, each combatant's initiative is a DEX check posted as an "Initiative roll" card (so `rollAll()` at combat start posts one per combatant); on `basic` it is DEX (+ 50 with Draw gun) and nothing is posted. Rollbox sets initiative through that same call, so a table on the optional rule still gets CoC7's cards.
- **CoC7's `rollInitiative` ignores `updateTurn`:** it writes the initiatives with `updateEmbeddedDocuments`, and Foundry's re-sort can move the current turn to someone else; Rollbox puts the turn back with `Combat#update({ turn })`, marked with its own option so its turn rule doesn't take it for a new turn.
- **Starting an encounter at the top of the order:** Foundry's `Combat#startCombat()` (build 370 `foundry.mjs`) is `update({ round: 1, turn: 0 })` after the `combatStart` hook, so everyone added and given an initiative before it starts round 1 at the top. Adding people after the start keeps the turn on whoever has it (a re-sort follows the current combatant), so a fight could carry on from the middle of the order: Rollbox's first blow makes the whole encounter, picks included, before `startCombat`.
- **A mid-turn initiative change skips people.** Foundry keeps the turn on the current combatant through a re-sort, so dropping the acting combatant below others who haven't acted moves the turn pointer past them, and End turn starts the next round. Rollbox changes Draw gun mid-round only for combatants whose turn hasn't come, with one exception: **a drawn gun put away** (holstered, or swapped for a weapon with no readied bonus). Traced (CoC7 8.15 `CoC7Combat._onToggleGun`): with Draw gun on, a click sets `flags.CoC7.hasGun` false, then `actor.rollInitiative(false)` (DEX; CoC7's optional rule rolls DEX and posts its card) and, off, always `Combat#setInitiative` (on, only when higher); Foundry re-sorts and keeps the turn on the current combatant. So Rollbox reorders nothing itself: it only fixes the turn pointer and who acts again. Whoever has already acted this round gets their turn skipped (`skipRound`) when the drop puts their place still to come; on their own turn, when the one who came after them now sits above them, the turn passes to that one (`Combat#update({ turn })`), as Place on standby does.
- **A dropped initiative on the acting combatant moves the turn's end:** CoC7's Draw gun turned off on the acting character (DEX + 50 back to DEX) can move them below people who haven't acted; a plain `nextTurn` would then start the next round. Place on standby notes who came after them first and gives the turn to that combatant wherever the re-sort put them.
- **Foundry's `Combat#nextTurn` from an `updateCombat` hook** runs the hook again for the new turn: a rule that skips turns must expect to be called while it is still running (Rollbox checks the skips again afterwards rather than nesting).
- **Two `updateCombat` handlers that each move the turn race.** Readying the guns at a round start (CoC7's Draw gun pressed, then `update({ turn: 0 })` to start at the top) and skipping standing-by turns (`nextTurn`) running side by side let a skip already on its way move the turn past the readied shooter who had just been put on top, so he lost his turn. Rollbox queues every turn start on the active Keeper's client and runs them one after the other, one skip per turn start; the `updateCombat` of its own `nextTurn` is the next item in the queue.
- **A combatant update with `combatTurn` changes the turn with no `updateCombat`.** `Combat#onModifyCombatants` (client `documents/combat.mjs`) puts the turn at the operation's `combatTurn` with `updateSource`, re-sorts, and fires only `combatTurnChange` (and `updateCombatant`). So Delay's move (`Combatant#update({ initiative, flags… }, { combatTurn })`) gives the next person the turn without any `updateCombat`: Rollbox's own turn-start work (who is in, a skipped turn passed) watches `updateCombatant` for the `delayedFrom` flag set this round. **`updateCombatant` fires before the re-sort** (seen in e2e: in that hook `Combat#combatant` is still the delayed one), so the turn's token is selected in the `combatTurnChange` that follows, still in the same task, before the panel's next frame.
- **Several turns skipped in one update:** `Combat#update({ turn: n }, { direction: 1 })` is what `Combat#nextTurn` does one place at a time (it also passes `worldTime`, 0 per turn by default, and fires the pre-update `combatTurn` hook, which a direct update doesn't). One `updateCombat` and one `combatTurnChange` fire for the whole jump, so a run of 40 skipped standing-by turns costs one turn start. `Combat#nextRound` covers a run that reaches the round's end.
- **Deleting the current combatant moves the turn on by itself:** `Combatant._preDeleteOperation` (client `documents/combatant.mjs`) simulates the turns without the deleted ones and, when the current combatant is among them, sets the operation's `combatTurn` to the next survivor (skipping defeated ones with Skip defeated on). So Leave out on the current turn's combatant needs no `nextTurn` of its own; Foundry's `updateCombat` doesn't fire for it (the turn is set through the operation), only `deleteCombatant`.
- **A preview of the turn order is only drawing:** Delay's live preview reorders the panel's entries (`turn-order.js` `previewDelay`), never Foundry's `Combat#turns`; the move itself is still one `Combatant#update` with `combatTurn` at Confirm. Drawn only while the controls act for the current turn, so a pick elsewhere never shows a moved order.
- **A new fighter widens the range:** who joins at a turn start is measured from every fighter, so someone the Keeper adds from the joining card can bring their own neighbours into range at the next turn start. That is the rule as built, not a bug.
- **Foundry's Toggle defeated also kills a CoC7 character.** The tracker's `_onToggleDefeatedStatus` sets `Combatant#defeated` and toggles `CONFIG.specialStatusEffects.DEFEATED` on the actor, which is `"dead"`: in CoC7 that is the Dead condition. So Rollbox marks someone unconscious or dying defeated with `Combatant#update({ defeated })` only. `Combatant#isDefeated` is `defeated || actor.statuses.has("dead")`, so CoC7's Dead counts already.
- **Foundry skips defeated turns only with its Skip defeated option** (`core.combatTrackerConfig.skipDefeated`, off by default): `Combat#nextTurn` then looks for the next turn that isn't `isDefeated`. Rollbox's turn rule moves past a defeated turn itself with `nextTurn`, so the two work together whichever way the option is set. **Skip defeated is a public getter:** `Combat#settings.skipDefeated` (`CombatEncounters.settings`, from `core.combatTrackerConfig`); `Combat#nextTurn` and `nextRound` read it, and so does Rollbox.
- **CoC7's chase is an item type** (`chase`, sheet `CoC7ModelsItemChaseSheet`): there is no call to open or start a chase with participants; a new Chase item (`Item.create({ type: "chase" })`) opens the chase tool, and its sheet's title reads "Chase: <item name>". Participants go in by dragging.
- **CoC7 asks about every new creature token** with rollable characteristics when its world setting `tokenDropMode` is "ask": a "Rollable detected" `DialogV2` (Roll all, Average all, Skip; Skip, the default, keeps the token as it is), one after another for tokens made together, on the GM's client, also for tokens made by code.

### Tokens and the board
- **Selecting on the map changes the Keeper's view:** controlling a token with vision shows that token's vision. So the Keeper's personal setting `rollboxTurnSelection` decides what a new turn does: Select (`Token#control`, the vision shown as any click would) or Keep (the selection untouched).
- **A token on the map from code:** `Token#control({ releaseOthers: true })` selects as a click does and fires `controlToken` synchronously (`canvas.tokens.controlled` is already up to date when it returns). Done in the turn change's own `updateCombat` hook, before the panel's next animation frame, so the panel draws the turn once; a delayed selection would let the panel draw the old selection's layout for a frame first. A turn Rollbox skips at once selects nothing: the skip's own `updateCombat` selects.
- **A row in Rollbox's turn order can stand in for a token while a target is picked:** every Rollbox picker turns on Foundry's Target tool (`ui.controls.tool?.name === "target"`); `Token#setTarget(true, { releaseOthers: true })` from a click there fires the same `targetToken` hook the pickers wait for.
- **`Token#center` reads the document** in v14 (`this.document.getCenterPoint()`). **A moved token's document lags during its animation:** a real drag (or keyboard move) goes through Foundry's movement: at `updateToken` (and `moveToken`, and a tick later) `TokenDocument#x` / `y`, and so `Token#center`, still give the place before the move, until the animation ends; `changes.x` and `document._source.x` hold the new place. Measured in a probe: a drag of 150 px, `updateToken` with `changes.x` 3213, `document.x` 3063, `_source.x` 3213. A direct `update({ x })` doesn't show it. Rollbox measures from `document.getCenterPoint({ x: _source.x, y: _source.y })` (`shared/distance.js` `tokenCentre`).
- **A token drag updates its document once, on the drop** (v14): nothing of Rollbox's runs while the mouse moves (0 redraws measured during a drag), and the Action flyout's distance redraw (`updateToken`) runs once per move.
- **An unlinked token's character keeps its own flags:** `setFlag` on a synthetic actor writes the token's `ActorDelta`; `ActorDelta#_onUpdate` then calls `Hooks.callAll("updateActor", syntheticActor, changed, …)`, so an `updateActor` hook sees a creature's flag change as it sees a world actor's (client source, `documents/actor-delta.mjs`). `game.actors` doesn't hold synthetic actors: look through `game.scenes` → `scene.tokens` with `actorLink === false` → `token.actor`. `fromUuidSync("Scene.<id>.Token.<id>.Actor.<id>")` resolves to that synthetic actor (`TokenDocument#getEmbeddedCollection("Actor")`).
- **Removing a user from a document's ownership in v14:** `{"-=<id>": null}` or `ForcedDeletion` in `ownership` is rejected ("is not a mapping of user IDs and document permission levels"); set that user's level to `CONST.DOCUMENT_OWNERSHIP_LEVELS.NONE` instead.
- **Foundry's Clear Chat** (`ChatMessage.deleteDocuments([], { deleteAll: true })`) removes every card from the chat log and the chat notifications on every client, CoC7's melee and defender cards included, and fires `deleteChatMessage` per message (Rollbox's being-attacked alert closes on it).
- **A world setting's saved value outlives a new default:** a world that saved `rollboxMeleeReach` keeps its value when the default changes; only worlds that never saved it get the new default. e2e steps that need the default set it themselves.

### Conditions and the combat tracker
- CoC7's conditions: `actor.conditionsSet` / `conditionsUnset` / `toggleCondition`; with status icons on they are active effects, so adding or removing one fires `createActiveEffect` / `deleteActiveEffect`, **not** `updateActor` (the panel listens to all three).
- **An open flyout must follow changes made elsewhere:** a status CoC7 sets (Prone from the token HUD is an active effect: `createActiveEffect` / `deleteActiveEffect`) and a weapon's ammo (`updateItem`) don't fire `updateActor`. The Action flyout redraws on those hooks.
- CoC7's Draw gun is the combatant flag `CoC7.hasGun`. Rollbox presses the button itself (its `onclick` is `CoC7Combat._onToggleGun`, called with a click event whose `currentTarget` is the button, so its promise can be awaited); CoC7 doesn't await its own `setInitiative`, so Rollbox waits for the combatant's `updateCombatant` (at most 1.5 s). The button exists only once Foundry's combat tracker has been drawn: `ui.combat.render({ force: true })` draws it with the sidebar on another tab. Its button re-rolls the actor's initiative with `actor.rollInitiative(hasGun)` and sets it with `combat.setInitiative`; when drawing, the new value is kept only if it's higher (`CoC7Combat._onToggleGun`).
- **How CoC7 stores and sets its conditions** (8.15, `STATUS_EFFECTS`: `tempoInsane`, `indefInsane`, `unconscious`, `criticalWounds`, `dying`, `prone`, `dead`): `actor.hasConditionStatus(key)` reads `system.conditions.<key>.value` only; `conditionsSet([key])` with status icons on creates (or updates) an active effect with that status (Dead with `flags.core.overlay`; `tempoInsane` with `flags.CoC7.realTime` and its duration in rounds or hours) and sets `system.conditions.<key>.value`; `toggleCondition(key)` is what each sheet's condition icon calls (`_onConditionToggle`, for the GM, or a player with CoC7's `statusPlayerEditable`): unset when on, set when off. So "set Dead as the Keeper would" is `toggleCondition("dead")` when Dead is off. **Bout of madness is `tempoInsane`**: CoC7 names it "CoC7.BoutOfMadnessName" and sets it from its Sanity card's real-time bout (`enterBoutOfMadness(true, rounds)`); there is no separate temporary-insanity condition.
- **CoC7 has its own dying CON roll that kills by itself:** with Dying on, its sheets show a Dying check button (`data-action="dying-check"`, `checkForDeath`), which posts `CoC7ConCheck.create(actor, { stayAlive: true })`; on a failed roll that isn't blind, its `rollCon` sets Dead itself (without `stayAlive` a failure sets Unconscious: the major wound CON roll). Rollbox's dying roll is a plain CoC7 CON check instead, so the Keeper decides (Mark dead).
- **A GM's roll of a player-owned character waits for its Roll:** a Keeper's click on CoC7's check link rolls for the selected token and, for a character with a player owner (online or not), posts the same unrolled card with a Roll button; its result comes in the card's update.
- **A link sent to the Keeper rolls the selected token, not the character it names** (reproduced): CoC7's link holds no actor, and `CoC7Link._onLinkClick` on a GM's client rolls once per controlled token (else the speaker's actor), whatever the request's text says. So a request whispered to the Keepers for someone else (an earlier build's request for an investigator whose player isn't online) rolled for whoever the Keeper had selected (Cecil, every time). Rollbox now rolls such a character privately for the Keeper at once (`send`'s `keeperRolls`) and never asks the Keeper to click a link for a named character. That includes a player-started NPC check (reproduced: a player's Assist with the Cultist of Dagon rolling, relayed to the Keeper's client, whispered "Your keeper has requested Cultist of Dagon make a … roll."; the Keeper's click with Cecil selected made Cecil's CoC7Check card). The relay's `send` now rolls that NPC privately on the active Keeper's client.
- **A GM's actor check of a player-owned character is a standby card:** CoC7's `characteristicCheck` / `skillCheck` / `attributeCheck` from a GM's client post an unrolled card with a Roll button (`check.standby = !config.preventStandby && stanbyGMRolls && game.user.isGM && config.hasPlayerOwner`); the three methods don't pass `preventStandby`. `actor.runRoll({ rollType: "R/CH", characteristic, … })` sets `preventStandby: true` by default and rolls at once, with the same `CoC7Check` card (`type: "characteristic"`, `key`) for `game.CoC7.messageResults`. The same for a sheet skill, `runRoll({ rollType: "R/SK", itemUuid, … })` (`normalizeRequest` reads `itemUuid`, then `skillId`, then `skillName`), and an attribute, `rollType: "R/AT"` with `attribute` (the Keeper's private roll for an investigator whose player isn't online).
- **The dice sound is played only when a message is created** (Foundry v14): `ChatMessage#_preCreate` sets `sound: CONFIG.sounds.dice` on a message created with rolls (`isRoll`), and `ChatLog#notify` plays `message.sound` for a new message; an update plays nothing. CoC7's check cards are created rolled, so they sound, whether from the sheet or Rollbox (Keeper's private rolls, a player's Make check). CoC7's attack cards (`CoC7ChatCombatMelee`, the ranged card) are created with no rolls and get them through an update when their roll button is pressed, so they are silent whether a person or Rollbox presses it; the standby card waiting for its Roll likewise. CoC7 plays no sound of its own (only Dice So Nice hooks). Rollbox adds none.
- `Combat#endCombat()` shows Foundry's confirm dialog before deleting; Rollbox's End combat confirms itself and calls `Combat#delete()`.
- **Foundry merges a flag's object on update** (`setFlag(scope, key, object)` is `update({ "flags.scope.key": object })`, merged recursively), so leaving a field out of a new value doesn't remove it: write `false` for every mark you mean to turn off (round notes).
- **Moving a combatant keeps the current turn on them.** `Combatant._preUpdateOperation` re-sorts a clone and sets `operation.combatTurn` to the moved combatant's new index unless the caller set it. To change someone's place and let the next person act (Delay), pass `{ combatTurn: index }` as the update's operation option. Restoring at turn 0 of a new round: `{ combatTurn: 0 }`, so the top of the restored order acts.

### Targeting (players)
- A click on a token with the Target tool active (`game.activeTool === "target"`) calls `Token#setTarget`, which goes through `TokenLayer#setTargets(ids, { mode })` (`replace`, `acquire`, `release`); every change fires `targetToken(user, token, targeted)` once per token, releases first. Players may target any token they can see, though they can't control it. Right-double-click on a token a player doesn't own also targets it, and the **T** key over a hovered token toggles its target.
- **Every user's targets reach every client.** `TokenLayer#setTargets` broadcasts them (`User#broadcastActivity({ targets })`) and each client applies them with `User#_onUpdateTokenTargets`, which fires `targetToken(user, token, targeted)` there too: the Keeper's client sees a player's targeting as it happens. The same path untargets everything when that user views another scene or logs off, so an untargeting isn't always the user's own act.
- **Setting a user's targets from code:** `canvas.tokens.setTargets(ids, { mode: "replace" })` (Foundry public, build 370) replaces this user's targets with those token ids (an empty list clears them); the `targetToken` hooks fire synchronously inside it.
- **A Scene flag doesn't redraw the canvas:** `Scene#_onUpdate` redraws only for its dimensions, grid, embedded collections and weather; `setFlag` on the viewed scene is a cheap shared mark every client reads (`updateScene` fires with `changes.flags`).
- `ui.controls.activate({ control, tool })` is SceneControls' public way to change the active layer and tool (async; does nothing if nothing changes). `game.activeTool` is `ui.controls.tool?.name`.

### The module socket and players' clients
- **Foundry's module socket:** `"socket": true` in `module.json` (read only when a world launches: relaunch after adding it) gives the channel `module.<id>`; `game.socket.emit(channel, data)` reaches every *other* client, never the sender. The handler gets `(data, senderUserId)`: Foundry's server adds the id of the user logged in on the sending socket (build 370 `dist/server/sockets.mjs` `handleCustomSocket`: `emit(event, data, this.user.id)`), so use that, not an id written in the message. Answer only from `game.users.activeGM` (`roll-requests/relay.js`).
- **A world setting's `onChange` runs on every client** (Foundry's `ClientSettings` on the setting's update), which is how a Keeper's change to a Player Rollbox feature redraws each player's menu without a reload. `game.settings.set` from code doesn't show Foundry's reload prompt for a `requiresReload` setting (only the settings form does).
- **A whisper always shows to its author.** A card meant for the Keeper alone must be made by the Keeper's client (the weapon-drawn notice, now a pop-up, is still shown only by the Keeper's client): a player's client asks it through the relay (message type `notice`, `roll-requests` `onKeeperRequest`), and the Keeper's client checks the player owns the character (`Document#testUserPermission(user, "OWNER")`) and, for a drawn weapon, that it is on that character's sheet.
- **CoC7's Keeper-only controls aren't on a player's copy of a card.** CoC7's `renderChatMessageHTML` handler removes every `.keeper-only-block` for a player (unless trusted with its `trustedCanSeeChatCard`) and only disables `.keeper-only-control`: the melee card's Automatic success and the whole of the ranged card's target block (its Under cover, Point blank, In melee, Reloading and its dice slider) are missing from a player's copy, while the melee card's dice slider and pool keys are there, disabled. A player's client waiting for a Keeper-only toggle must read it from the card's flags, not look for the button: `flags.CoC7.load.isAutoSuccess`, `aiming`, `poolKeys` and `poolModifier` (melee), and the active target's `targets[i].poolKeys` / `poolModifier` (ranged; `poolModifier` saved as a string). A toggle read from the flags is judged against the card's first render, so a dice count is compared with where the card started.
- **An NPC's check of a skill not on its sheet** is rolled by Rollbox as CoC7's raw roll at the base value (`runRoll` with `MANUAL_ROLL`), so `game.CoC7.messageResults` gives a plain value result (`type: "value"`, no `key`), not a skill: a watcher for a named skill must accept it for that target.
- **CoC7's opposed card has its result when every side is rolled:** `game.CoC7.messageResults` gives one result per side (`isRolled`), whatever the outcome ("Both side failed." included). Start Rolls with no player online rolls both sides in one update, which can land before Rollbox's notice names its card: check both on the card's update and on the notice's.
- **A player's own check:** CoC7 posts an unrolled card (its "standby" card, `roll-standby.hbs`) only from a GM's client (`check.standby = … && game.user.isGM`, `apps/roll-normalize.js`). On a player's client `actor.characteristicCheck` / `attributeCheck` / `skillCheck(key, false, options)` opens CoC7's roll dialog (`CoC7RollDialog`, classes `coc7 dialog bonus-selection`, its Roll button `[data-action=ok]`) with the given `difficulty` and `poolModifier`, and posts the `CoC7Check` card in the roller's roll mode once they roll; the dialog is made with `rejectClose: true`, so closing it rejects the call (Rollbox doesn't await it). A combined check through `_onLinkActorClick` on the player's client posts CoC7's combined card (CoC7 asks the Keeper's client to make it through its own socket), which waits for the player's roll. Rollbox passes `fastForward` true (Make check rolls straight into chat), so the dialog no longer opens.
- **A player's being-attacked alert and the Keeper's side of it start at `ready`** with the Player Rollbox on, on both clients: after turning the switch on, reload the Keeper's page as well as the player's (Foundry's settings form does this with its reload prompt).

### Selection hook and the panel's place (Foundry v14 build 368)

Clicking a token releases the others first (one call each); a box-select fires many. Coalesce to one redraw per frame.

The list grows upwards as players join, so the panel stays put. Only when `#interface` is missing does the panel fall back to the column, just before `#players` (`margin-top: auto`, `pointer-events: all`; not inside `#players`: Foundry replaces that element's contents on each render).
- **Built:** the panel is 200px wide in the column; its buttons and flyout are absolutely positioned to its right (`left: calc(100% + var(--rollbox-gap))`, bottoms aligned), so the column keeps its width and they overlay the canvas. The column has `pointer-events: none`, so each card, the button column and the flyout set `pointer-events: all`. (Checked by the maintainer in Foundry: position, width, look and numbers correct; players see no panel.)
- **Opening a sheet:** CoC7 8.15's actor sheets are ApplicationV2 (`CoC7ModelsActorCharacterSheetV2` and others); `ApplicationV2#render(true)` is treated as `{force: true}` (`client/applications/api/application.mjs`).

### Moving the panel (Foundry v14 build 368)

- **Where a moved panel goes:** Foundry's `#interface` (`templates/views/game.hbs`): the element holding `#ui-left`, `#ui-middle` and `#ui-right`, `position: relative` and stretched to the screen by `body.game` (a fixed flex row). Foundry never draws it again, and the camera dock is placed beside it (`CameraViews#_onRender` puts `#camera-views` before or after `#interface`), so `#interface` shrinks to leave room for it. The panel is appended to it, positioned absolutely, at the Panel layer's `z-index` (below). Not moved, it floats in `#interface` beside the players list ("Selection hook and the panel's place"), at every Panel layer.
- **Set the moved panel's position, size and stacking inline**, never only in a stylesheet: Foundry reads a module's `module.json` (and so its `styles` list) only when the world is launched, so a stylesheet added to `styles` isn't loaded after an F5, only after Return to Setup and launching the world again. A moved panel whose floating rules aren't loaded stays a static flex item in `#interface`, its offsets push it off the bottom of the screen, and that spot is saved, so it never comes back. So: inline styles, a check after every placement that the panel's own box is where it was put (else it docks), and a saved spot that is off screen or unreadable is ignored. (confirmed)
- **UI scale:** the left column carries Foundry's UI scale as a transform (`#ui-left { transform: scale(var(--ui-scale)) }`; `--ui-scale` is set on `body` by `Game#configureUI`). Outside the column the panel multiplies it in itself: `transform: scale(calc(var(--ui-scale, 1) * <Panel size>))` from the anchored corner.
- **The spot** is measured from the corner of the screen quarter the card was dropped in (`{corner, x, y}`), so a resized window keeps the panel near the same edges and a taller card grows away from the edge; it is clamped to the screen when placed, without changing the saved value.
- **Menu and flyouts mirrored by classes** (`position.css`): `rollbox-menus-left` puts the side at `right: calc(100% + gap)` in `row-reverse`; `rollbox-grow-down` puts the side at `top: 0` and pulls the menu up by its extra buttons (`--rollbox-extras`), so Action, Check and Other stay level with the character panel's top. An open flyout running off the screen shifts the panel by the overflow of the panel, `.rollbox-side` and `.rollbox-menu` boxes together, without saving it.
- **Dragging:** pointer events on the document while a header is pressed (no pointer capture: moving the element into `#interface` would end it), 4px before a press counts as a drag. Images in the cards get `-webkit-user-drag: none`, or Chromium starts its own image drag and cancels the pointer.
- **Foundry's layout, measured from build 368's `foundry2.css`:** `#ui-left` has 16px padding and gaps, `#ui-left-column-1` is 72px (two 32px control columns and an 8px gap), `#ui-left-column-2` (scene navigation) 200px; the sidebar is its tab strip then `#sidebar-content` (`--sidebar-width` 300px), which slides off to the right when collapsed; `#chat-notifications` and, when the sidebar is collapsed, the chat input live in `#ui-right-column-1` beside it; `#hotbar` is centred in `#ui-middle`, 60px tall with a 16px bottom margin.

### Panel layer (Foundry v14 build 370)

- **Foundry's stacking, measured in build 370:** windows (`.application`, ApplicationV2) are children of `<body>` at `--z-index-window` (100); `ApplicationV2#bringToFront` gives the window `++ApplicationV2._maxZ` (a static counter that starts at `--z-index-window` read from `body`, and that Foundry's own popups such as the ProseMirror menus also take). `#interface` (`position: relative`, no `z-index`, no transform) makes no stacking context, so an element inside it competes with the windows directly. `#ui-left`, `#ui-middle` and `#ui-right` are `position: absolute` at `--z-index-app` (30) with a transform, so each is a stacking context: nothing inside the left column can be drawn above a window. Tooltips are `--z-index-tooltip` (9999), the tour overlay tooltip − 2 and − 1, notifications `--z-index-notification` (99999); right-click menus (`ContextMenu#_setFixedPosition`) are `popover` elements and modal dialogs use `showModal()`, both in the browser's top layer, above any `z-index`.
- **The setting** `rollboxPanelLayer` (`panel/layer.js`): **Bottom** `var(--z-index-app, 30)`; **Top** `calc(var(--z-index-tooltip, 9999) - 3)`, above every window and under tooltips, tours, notifications, right-click menus and modal dialogs; **Top when active** (default) starts at `var(--z-index-window, 100)` and takes `++ApplicationV2._maxZ` (capped at 99999, as Foundry caps its older windows) on any `pointerdown` on the panel (a capture listener), so it interleaves with windows exactly as a window does. **Top when active or selected** (`activeOrSelected`) stacks as Top when active and also takes the next number when tokens are selected, as if the panel had been pressed (`forwardOnSelect`: a second `controlToken` hook, `noteSelection`, marks a new selection and the next redraw brings the panel forward; a redraw for any other reason, such as an actor update, doesn't). `_maxZ` is an internal: guarded, and without it Top when active works as Bottom (one warning). Applied at once by the setting's `onChange`; the flyouts are inside the panel, so they follow its layer. **A press on a window**: `ApplicationV2#bringToFront` gives a new number only when the window isn't already Foundry's front window (`#frontApp` and `ui.activeWindow`); the window that was in front before the panel was pressed keeps its old number, so it would stay under the panel. A capture `pointerdown` listener on the document (it runs before the window's own) drops a front panel to the pressed window's `z-index`; with the same number the window, later in `<body>` than `#interface`, is drawn on top (measured in build 370 by the e2e check).
- **Foundry's own keys over the canvas (build 370):** Tab is Foundry's "cycle tokens" key (it changes the selection) and Escape releases the selected tokens and closes windows, both handled on `window`. An e2e step that presses either must expect that, or stop the key before it reaches `window`.
- **Beside the players list, at every layer**: the panel floats in `#interface` beside the list (`besideList`), scaled by Panel size times `--ui-scale` from its bottom-left corner, the menu to the right; the Bottom layer's `z-index` is the left column's, so windows still cover it. A `ResizeObserver` on `#players`, `renderPlayers` and the window's `resize` place it again. It doesn't follow anything that moves or hides `#ui-left` as a whole.

### The menu host

- **`registerFlyout(id, { title, render, staysOpen, columns })`** (`panel/menu-host.js`): each flyout part plugs in from its own `register…()`; every flyout, Opposed included, opens beside the menu, and the menu stays visible. The menu is Action, Check and Other, which never move, with the extra button (Opposed, two selected) above them; Sanity is a tab of Check and Assist a tab of Other, so neither registers. `staysOpen: true` keeps a flyout open while anything is selected even when its button isn't offered, and lets `open(id, start)` open it then (`open` asks `offers(id)`): the Opposed flyout, opened from a right click with one or three-plus selected. `render` gets `selectionChanged` so a flyout can keep its choices over a selection change, and `open(id, start)`, the host's own, so a flyout can open another (a Check row's Right click opens Opposed). `columns` gives the character cards' value columns while that flyout is open (Other on Assist), and `render`'s context gets `cardChanged()` to redraw the card when they change. A player's panel passes its button ids to `update(actors, ids)` (`player/` `playerMenu()`), so the host draws only those, with no extras, instead of hiding buttons.
- **Opening with a starting state**: `host.open(id, start)` opens a flyout with a starting state (Check: `{tick, add, plain, send, focus, tab}`; Other: `{section, plain, send}`; Opposed: `{first, picks, create}`, built by `flyouts/opposed` `opposedStart(actor, key, {create, first})`). The render's context gets `start` and `setTitle(text)` (Other's title follows its section), and a render may return a controller `{ apply(start) }`: while that flyout is open, `open` with a start calls `apply` instead of drawing it again, so the Keeper's other choices stay. A send asked for by a start goes through the flyout's own send, so its result line is the flyout's.
- **Every control lives inside the open flyout**: the character cards and character sheet show information only. Exceptions: with moving allowed, dragging a card header moves the panel; the character sheet's characteristics, SAN and Luck (each character's numbers on the two-character sheet) are buttons that open their flyout with CoC7's sheet shortcuts (`panel/sheet-clicks.js`; design/panel.md, "The character sheet's values"); a character card's portrait is a × that deselects its token (`Token#release`). a click elsewhere on a character card selects only that character (`Token#control`), and a right click on any character targets their token (`Token#setTarget`; a value's own right click stays its own). Rollbox never calls CoC7's sheet handlers for them.
- **No keys taken**: every button, input, select and text area Rollbox draws gets `tabIndex = -1` in `utils.js`'s `element()`, so Tab never stops on the panel, and Rollbox installs no `keydown` listener outside its own text boxes (Enter in a value line or the skill search). A click still focuses a text box.
- **Shared controls** (`scripts/shared/`, [docs/shared.md](shared.md)): the value line, the compact dice picker, the Blind toggle, the status line, and `flyout.js`'s helpers (tabs and search, how rows, the main button's words, the Send runner and the result). The dice picker writes the formula text the requests take ("1D4+1", "1D6+DB", "1D4+½DB"); each flyout passes its own rule for the value line (`sanityLoss`, `damageText`). The dice are matched longest first in its parser, or "1D100" reads as D10 and 0.

### CSS: layers, scoping and variables

- **Cascade layers:** Foundry puts its CSS in layers (`reset, variables, elements, blocks, applications, compatibility, layouts, system, modules, exceptions`) and loads a module's `styles` into the `modules` layer unless `module.json` names another (build 368 server `view.mjs`). So Rollbox's rules beat Foundry's element and application styles and CoC7's `system` styles without `!important`; only the `exceptions` layer beats them.
- **Foundry's own look:** Foundry's players card and scene control buttons use `--color-cool-5-75` (background), `--color-cool-4` (border), `--color-cool-3` (hover border) and `--color-warm-2` (active border) (`foundry2.css`, build 368). Rollbox's dark palette starts from them, with fixed light text colours (`--color-light-1/2/4`), because Foundry's themed text colours turn dark under its light interface theme while Rollbox follows its own Theme setting.
- **Variables on `.rollbox-panel`:** sizes `--rollbox-width` (200px, Foundry's `#players-active`), `--rollbox-gap` (8px), `--rollbox-radius` (8px), `--rollbox-col` (`calc(1.8 * var(--font-size-12, 12px))`, one character-card value column, three digits wide, so names run up to it; JS sets only `--rollbox-cols`, the number of columns), `--rollbox-second` (the bottom character's tan on the two-character sheet), `--rollbox-sheet-height` and `--rollbox-button-gap` with `--rollbox-button-height` worked out from them, `--rollbox-row-height` / `--rollbox-row-gap` (lists), `--rollbox-scale` (Panel size), `--rollbox-opacity` (Panel transparency), `--rollbox-color` (Panel colour); and the theme's palette (below). Every flyout's CSS uses only these, so redefining them on the panel restyles every flyout.
- **`shared.css` order:** loaded right after `panel.css` and before every flyout's file, so it is the base and a flyout's own rule of the same weight wins. One rule, `.rollbox-panel [hidden][hidden] { display: none }`, keeps anything hidden hidden: two attribute selectors outweigh any one-class rule under `.rollbox-panel`, so neither the flyouts nor the panel need `[hidden]` lists (only `.rollbox-panel[hidden]` itself has its own rule). Generic classes from `flyouts/flyout.js` (`rollbox-btn`, `rollbox-segment`, `rollbox-tab`, `rollbox-line`, `rollbox-input`, `rollbox-list`, `rollbox-row`, `rollbox-result` …) carry the shared look; a flyout's own class stays only where its CSS or a test selects by it.
- **Flex lists of buttons:** a button with `min-height: 0` in a column flex box with a `max-height` shrinks below its text, and the rows overlap instead of scrolling. Give the rows (and everything between them and the scrolling box) `flex-shrink: 0`.
- **Foundry's radio buttons and tick boxes** are drawn as Font Awesome glyphs in `::before` / `::after`, sized by `--checkbox-size` (`var(--font-size-20)`, 20px), not by the input's box (`appearance: none`). Shrinking the input with `width` / `height` alone leaves the glyph at 20px, overflowing below it; in a scrolling list the last row's glyph made the list scroll. Set `--checkbox-size` on the input too (`shared.css` does for every list row).
- **Chromium features used** (Foundry's Electron): `color-mix()`, `:has()`, `field-sizing: content`, `writing-mode: vertical-rl`, the `inert` attribute.

### Sizes: Panel size, buttons, lists

- **Panel size:** `transform: scale()` with `transform-origin: left bottom` on the panel, not `zoom`: a transform leaves the element's layout box alone, so the panel's place above `#players` doesn't move and the scaled panel grows up and right over the canvas, never over the players list. No transform at 100%. Anything with a `max-height` in `vh` inside the panel must divide it by `--rollbox-scale` to stay on screen (the flyout does).
- **Measuring:** `offsetHeight` is the layout height and ignores `transform`, so the Panel size's `scale()` doesn't change it; it is 0 while the element or an ancestor is `hidden`. Chromium's computed `rowGap` gives a flex column's `gap` in pixels.
- **The menu's buttons have one fixed height, set in CSS**: no script sets `--rollbox-button-height`. In `panel.css` it is `calc((var(--rollbox-sheet-height) - 2 * var(--rollbox-button-gap)) / 3)`: three buttons and the two gaps equal the one-character sheet at 100%, measured once in Chromium with Foundry's own stylesheet and fonts (`--rollbox-sheet-height` 182px; `--rollbox-button-gap` 6px, which the button column's `gap` also uses), so 56.67px. Changing the gap keeps them matched. Action, Check and Other fill the bottom 182px of the character panel; the extra button (Opposed) reaches above them. Don't measure it in JS: with eight names the invisible character sheet under the character cards is as tall as the cards, so the buttons would grow with it.
- **Lists that must show ten rows** set every row's height to a CSS variable built from the font-size variables and line heights (`calc(6px + 1.25 * (var(--font-size-12) + var(--font-size-10)))`), and `max-height` to ten of them plus the gaps, so it holds at any font size; a fixed pixel `max-height` didn't (a table check: 365px scrolled at nine names).
- **A list that scrolls inside content drawn anew** (the turn order's standing-by group: five compact rows, then it scrolls): the panel replaces its content on every change, so the new list starts at the top. The part keeps each list's `scrollTop` from its `scroll` events and puts it back a tick after drawing (`setTimeout`: scrolling needs the list's layout, which exists once the panel has attached it), and scrolls a row into view only when it is a different combatant from last time; otherwise a redraw would pull the list back to the selected row after every scroll. A theme whose rows are taller (Art Deco 36px, CoC7 minimal 34px, set on the row itself) restates the row height for the list's `max-height`, and with a 2px padding to keep an outline drawn outside a row (`box-shadow`) inside the scrolled box, adds those 4px too (Foundry's `box-sizing: border-box`).
- **The character panel never changes width**: `--rollbox-width` in every state; highlights are drawn inside a card, never as an outer border.
- **The character cards are never shorter than the character sheet:** the character panel is one grid cell holding an invisible copy of the first character's sheet (`sheetGhost`) under the character cards.
- **Auto-hide** (`rollboxAutoHide`, `rollboxAutoHideAfter`; Keeper and players): after the set time without the pointer over the panel or a press on it, the one- or two-character sheet drops to the compact character card. `pointerenter`, `pointerdown` or a new selection brings the full sheet back and starts the wait again; `pointerleave` starts it. A provider's content (combat's turn order) and three or more characters are never changed. Details: [docs/panel.md](panel.md), "Auto-hide".

### Appearance: themes, colour, transparency

**Never highlight one side of a border** (also in CLAUDE.md's Rules): no coloured or thicker stripe on only one of an element's four borders (`border-left: 4px solid …`, a one-sided inset shadow) to mark a selected, warning, new or active state, in any theme or mockup. Use a full border, a fill, the text colour or the element brightening instead. A plain line on one side that marks no state (a divider between rows or parts) is fine. `panel.test.mjs` ("no one-sided border highlight") fails on a one-sided border in a selector for a state (`:hover`, `:focus`, an ARIA state, or a class ending `-selected`, `-picked`, `-current`, `-active`, `-warning`, `-new`, `-pressed`, `-primary`, `-now`, `-held`, `-greyed`, `-on`…), on a one-sided inset shadow or mixed border widths and colours anywhere, and on a one-sided border set from a script; a new state class takes one of those endings.

- **Three themes, skins over one panel**: the personal Theme setting (`rollboxTheme`: `foundry`, `artDeco`, `coc7Minimal`; any other saved value, such as `dark` or `light`, reads as `foundry`) puts one class on the panel root (`rollbox-theme-foundry`, `-art-deco`, `-coc7-minimal`, `theme.js` `THEME_CLASSES`). Every part's CSS uses only the palette variables (`--rollbox-bg-solid`, text, strong and muted text, placeholder, disabled, borders, accent and accent text, the red warning, Assist's coral target, the Defender blue, the empty tick box, button fill, bar track, the pressed look, and the HP, MP, SAN and Luck bars `--rollbox-bar-*`), never a colour of its own; each theme redefines them. The CoC7 themes live in `scripts/panel/themes/` (`art-deco.css`, `coc7-minimal.css`), listed last in `module.json` so their rules beat a part's own rule of the same weight; their shapes (window bars, ribbons, blocks) restyle the parts' existing classes and never change a layout box the clicks depend on (the e2e `themes` area compares the menu buttons' and the flyout's places with the Foundry theme's).
- **The Foundry theme follows Foundry's interface:** `Game#configureUI` (Foundry build 370 `client/game.mjs`) puts `themed theme-dark` or `theme-light` on `#interface` (from `core.uiConfig` `colorScheme.interface`, or the browser's scheme when that is "default") and on sidebar and HUD windows; `body` gets the applications scheme. There is no hook for it: the settings window calls `configureUI` to preview a choice before saving, and the `clientSettingChanged` hook fires only on save. So the panel reads `#interface`'s class and watches it with a `MutationObserver`; in Light it adds `rollbox-theme-light`, and `panel.css` redefines the palette under it. Every text colour of both palettes has at least 4.5:1 contrast on the solid background (WCAG AA); disabled text and the empty tick box at least 3:1 on the default colours.
- **The Panel colour is the Foundry theme's tint:** the panel shows the picked colour itself when the palette's text reads well on it, otherwise its HSL lightness mirrored (L → 100 − L) and kept readable (WCAG relative luminance at most 0.05 under Dark, at least 0.57 under Light), hue and saturation kept. Nothing is saved: the setting keeps what was picked, whatever Foundry's interface does. The CoC7 themes ignore it.
- **CoC7's look, at runtime** (CoC7 8.15): CoC7 defines its sheet variables only inside its own windows (`.application.coc7`, and `.themed.theme-dark.application.coc7` for dark), so a module's element can't inherit them: Rollbox restates the values (dark: `--color-labels` `#b44849`, `--color-window-decoration` `#274914`, `--color-active` `#ffa`, HP/MP/Luck/Sanity as `color-mix(in oklab, base, #fff 15%/50%)`, `--background-sheet` `assets/art/page-dark.webp`). Its sheet fonts are `--investigator-sheet-primary-font: customSheetFont, "Modesto Condensed"` and `-secondary-font: customSheetFont, "Lusitana"`; `customSheetFont` is a document-wide `@font-face` CoC7 writes from its "Override sheet artwork" settings, so a module can name it too; Modesto Condensed ships with Foundry (`CONFIG.fontDefinitions`); Lusitana ships with neither, so it shows only where installed (Rollbox falls back to Georgia). The images (`assets/images/sheet-v3/`: `line-red.webp` 1500×10, `ornament-top.webp` 1500×45 with the zigzag's peak just left of centre, `line-ornament-green.webp` 1500×57 with the tentacles at the right end, `tentacles.webp` 50×31, `ribbon-red/green/yellow/blue.webp` about 92×76, hanging down with the forked end at the top; `assets/art/page-dark.webp` 1300×1300) are used by URL (`foundry.utils.getRoute("systems/CoC7/…")`, so a route prefix is kept), set as CSS variables on the panel by JS, never copied. CoC7 turns its ribbons with `rotate: -90deg` for its left-hand tabs; Rollbox turns them 90° the other way to run out to the right. A missing image is found with one HEAD request each (Foundry's static file server answers HEAD). The ornament's dip (measured from its pixels): under the peak the two lines rise into a chevron whose inner edge runs from about y 10 at x 735 to y 22 at x 590 and 870, then drop as walls at about x 600 and 865 to the image's bottom (rows 22–41 of 45), so the space between the walls is about 265px of the 1500px image (177px at Rollbox's usual 1000px, 204px at the 1150px the Action, Check and Other flyouts use to fit three tabs); the lines' low parts sit in rows 28–41. In `line-ornament-green.webp` the two green lines take rows 41–56 of 57 and the tentacles x 1297–1451 above them; turned upside down at 34px high, the lines take a band's top 10px.
- **Foundry's own controls:** Foundry colours placeholders and tick boxes from its interface theme through variables (build 368 `foundry2.css`): `--input-placeholder-color` on `input, select, textarea`, and `--checkbox-background-color`, `--checkbox-checked-color`, `--checkbox-disabled-color` (also `--checkbox-checkmark-color`, `--checkbox-size`) on tick boxes and radios, set per theme with `body.theme-light` / `.mixin-theme-light-forms`. Rollbox sets the same variables on its own inputs from its palette (`shared.css`); its `modules` layer beats Foundry's.
- **Transparency:** one variable on the panel, `--rollbox-opacity`; every background is `color-mix(in srgb, <the solid colour> <opacity>, transparent)`, so text keeps full opacity. Foundry's own players card is `--color-cool-5-75` (75% opaque, i.e. 25% see-through); Rollbox's default is 25%, the same look. A light background shows the map through more, so the Light theme lets half as much through for the same setting: `calc(50% + var(--rollbox-opacity) / 2)` as `color-mix`'s percentage (Chromium accepts `calc()` there).
- **Colour and transparency together:** the colour sets `--rollbox-color`, the solid background; the transparency mixes it with `transparent` through `color-mix`.

### Events, clicks and redraws (Foundry v14 build 370)
- **Foundry's buttons ease every change** (`button { transition: 0.5s }` in `foundry2.css`) and outline a clicked, focused button: a selection border taken away fades out over half a second. Rollbox's panel sets `transition: none` on its buttons and drops the outline on a mouse focus (`:focus:not(:focus-visible)`).
- **Foundry's Escape** is handled on `window` (bubbling): a capture-phase `keydown` listener on `window` sees it first, and `stopImmediatePropagation()` there keeps Foundry from also closing a window or releasing the tokens for that key press.
- **Foundry's map zoom listens to the wheel on the window, bubbling** (`MouseManager#onWheel`, `helpers/interaction/mouse-manager.mjs`), and only acts when the element under the pointer is the board. A `wheel` listener on the window in the capture phase (`{ capture: true, passive: false }`) that calls `stopImmediatePropagation()` and `preventDefault()` runs first and keeps the wheel from Foundry and from page scrolling; Rollbox adds it only while the panel is held.
- **A drag over buttons still ends in their click:** the browser sends `click` to what was pressed when the pointer comes up over the same element, and a panel that moves with the pointer keeps it under the pointer. Swallow one `click` in the capture phase right after a drag (and drop the listener on the next tick) so a drag never presses or selects anything.
- **`contextmenu` on a Rollbox element** inside the panel isn't Foundry's: Foundry's canvas context menu only listens on the board, so a row's right click can be Rollbox's (`preventDefault` keeps the browser's menu away).
- **A right click inside a right-clickable card:** Rollbox's values (Opposed from a characteristic) and the card around them (target the character) both listen to `contextmenu`. The inner one calls `stopPropagation()` after `preventDefault()`, so one right click does one thing; a `contextmenu` that starts no drag is safe beside the panel's drag, which takes only the main button (`event.button === 0`).
- **A click on a card that also holds a button:** a button inside a clickable row (a character card's ✕) stops its own `click` from reaching the row, or the row's "select only this one" would run after the ✕'s deselect.
- **A child can't undo its ancestor's opacity:** greying a flyout with `opacity` on a wrapper keeps every button inside it grey, even one that should brighten on hover (the Keeper's Override). Grey the parts beside the button's path instead and the button on its own (`flyouts/action/index.js` `greySpent`). A button that must react to hover can't be `disabled` either: the Keeper's greyed Override and greyed Flee are ordinary buttons with a class, and a capturing click listener (or the toggle's own confirm) asks first.
- **A `ResizeObserver` callback runs after the browser's layout and before paint**, so a panel placed from it is never seen out of place, and a redraw that changes no observed size costs no layout of Rollbox's own. Placing the panel right after rewriting it forces a layout in the middle of the frame.
- **The panel's redraw forces a layout:** `panel/position.js` `place()` (`dockBeside` and `shiftIntoView`) reads boxes right after the redraw rewrote the panel, and again after setting its position. It is most of Rollbox's own time per redraw in a big fight (about 5 ms of a redraw at 50 combatants on the test PC), but the layout would mostly happen at the next frame anyway.
- **`game.settings.registerMenu` needs an ApplicationV2 (or FormApplication) subclass** as `type`, and Configure Settings draws a module's menus before its settings; a subclass whose `render` does something else and draws nothing works as a plain button.
- **A set of choices as tick boxes in Configure Settings:** a setting whose `type` is a `SetField` of a `StringField` with `choices` is drawn by `SettingsConfig` through the field (`formGroup`), as Foundry's `<multi-select>` drop-down. Registering it with `input: (field, config) => foundry.applications.fields.createMultiSelectInput({ ...config, type: "checkboxes", options })` draws `<multi-checkbox>` instead, one tick box per choice; the form saves the ticked values as a list. `game.settings.get` returns a `Set` (the field initialises it), so code reads it with `Array.from`; a `Set` passed out of a Playwright `page.evaluate` arrives as `{}`, and saving `{}` stores an empty list.

## Settings

Every setting belongs to a section, and each section belongs to one feature switch at the top of the page, which greys it out while off.

| Scope | Stored | Use for | Note shown |
| --- | --- | --- | --- |
| `world` | On the server, one value for everyone; only the Keeper can change it | Rules that must match for everyone | Keeper setting, applies to everyone. |
| `user` | On the server, per user, follows them to any device | Personal preferences | Personal setting, affects only your screen. |
| `client` | One browser only | Device-specific values | Personal setting, affects only your screen. |

- **Features on top, sections below**: the page opens with a box of the primary features' switches (`settings.js` `FEATURES`: `rollboxEnabled`, `rollboxPlayerRollbox`, `rollboxCombatPanel`, `rollboxGameplay`, `rollboxSetupCheck`), each an ordinary setting registered first. Then one box per feature (`SECTIONS`: `{ id, feature, title, groups: [[label, keys]], indent, menus }`): a heading (Foundry core `h4.border`, margin-bottom 0, like CoC7's own settings) with who it's for (Personal, Keeper or Mixed, from the scopes) and the feature it follows, its settings in small labelled groups, a setting that only matters with another indented. While the feature's tick box is unticked in the form the whole box is greyed (opacity 0.45); display only: nothing is disabled or saved, and the parts read their own switches. No section has a switch of its own, so a new setting needs no new key beyond itself: put it in the section of the feature it belongs to. The decoration (boxes, notes, greying) is `settings.js`'s, a change from `void-coc7-modules`' per-section masters to merge with that module later.
- **A setting's own flags** (stripped before `game.settings.register`): `note` (the italic scope line), `reset`, `button`, `format`, `foundryOnly` (greyed while a CoC7 theme is picked) and `keeperOnly` (a personal setting that does nothing for a player: hidden on a player's page).
- **The page order is the registration order** (Foundry lists a module's settings in the order they were registered, after its menus: build 370 `SettingsConfig#_prepareCategoryData`), so `settings.js` registers in page order. The boxes are built by moving Foundry's own `.form-group`s into Rollbox's `div[data-coc-section-box]`s inside the module's category section; the form still submits them by name.
- **The sections, in page order** (`settings.js` `SECTIONS`). The parts' `declareSettings()` lists are turned into entries by `settings.js` `declared()`, which makes `label` Foundry's `name` and drops `key` and `section`. Every part document's "Settings" lists its keys in full.
  1. **Rollbox panel** (follows `rollboxEnabled`, "Rollbox panel": user scope, Boolean, default true, reload; `panel/settings.js`): Look: `rollboxTheme` (`foundry` / `artDeco` / `coc7Minimal`), `rollboxColor` (`ColorField`, default `#0b0a13`) and `rollboxTransparency` (0–70 step 5, default 25), both indented, `rollboxScale` (80–250 step 10, default 100), each of the four with a Reset button, `rollboxNoticeScale` (`combat/notice-place.js`), `rollboxCardMeters`; Placement: `rollboxMovable` (**client** scope, with Reset position), `rollboxMenuSide`, `rollboxPanelLayer` (`panel/layer.js`), `rollboxAutoHide`, `rollboxAutoHideAfter` (indented, its time beside the slider); Behaviour: `rollboxShowPlayers` (`keeperOnly`), `rollboxEscapeClosesFlyout`, `rollboxSimplifiedDice` (`shared/settings.js`); Menus: `rollboxCheckOpensOn`, `rollboxListStyle` (`flyouts/check/`), `rollboxSpellTextTab`, `rollboxSpellTextCasting` (`flyouts/action/spell-text.js`). Hidden: `rollboxOffset` (client), `rollboxNoticePlaces`. All personal, no reload. The position settings are client scope because a spot that suits one screen may not suit another.
  2. **Player Rollbox** (follows `rollboxPlayerRollbox`, "Player Rollbox": world, default on, reload, since `registerPanel()` reads it once at `ready`): What players can do: `rollboxPlayerActions`, `…Checks`, `…Combined` (indented), `…Opposed`, `…Assist` (world, default on, no reload: their `onChange` redraws each player's menu; `…Sanity` and `…Luck` registered hidden); Each player's own: `rollboxRollMyAttacks` (user; `roll-requests/attack.js`).
  3. **Turn order and turn controls** (follows `rollboxCombatPanel`, "Turn order and turn controls": user, default on; `combat/turn-order.js`): Your view: `rollboxTurnSelection`, `rollboxTurnOrderClick` (both `keeperOnly`).
  4. **Gameplay rules** (follows `rollboxGameplay`: world, default on; `combat/encounter.js`): Starting a fight: `rollboxJoinRange`, `rollboxNoticeDraw`, `rollboxNoticeRange` and `rollboxNoticeDistance` (indented); Firearms: `rollboxReadiedFirearms`, `rollboxBowsReadied` and `rollboxSwitchLosesReadied` (indented); Melee: `rollboxMeleeReach` (`flyouts/action/attack.js`); Rolling: `rollboxAutoRollNpc`, `rollboxAutoRollAttacks` (`roll-requests/attack.js`). World scope, read when used, no reload. The two Rolling settings act whatever `rollboxGameplay` says; the box only greys them.
  5. **Setup check** (follows `rollboxSetupCheck`, "Setup check at login": world, default on; `setup/`): the Check now menu (`rollboxSetupCheckNow`, a settings menu Foundry draws first in the tab; `settings.js` moves it into this box).
- **Configure Settings is a category browser in v14:** each module has a tab (`button[data-tab="<id>"]`) and a section (`section[data-category="<id>"]`); the search box only hides single settings (`hidden` on a `.form-group`). On a player's client with the Player Rollbox off, `decorateSettingsConfig` hides Rollbox's tab and settings with an inline `display: none` (`hideFromPlayer`), so players see nothing of Rollbox.
- **A setting without a hint** has no `.hint` paragraph in Configure Settings, so `addScopeNote` makes one (Foundry's `hint` class) to hold the italic note.
- **Drop-downs (build 368, `applications/settings/config.mjs`):** a setting with `type: String` and `choices: {value: label}` becomes a `StringField` with those choices, which Configure Settings shows as a select. The saved value is the key (`"typed"`), not the label. (assumed)
- **Sliders (build 368, `applications/settings/config.mjs`):** a setting with `type: Number` and `range: {min, max, step}` becomes a `NumberField` with those bounds, which Configure Settings shows as a range slider. `onChange(value)` runs on the client whose value changed (`client-settings.mjs`), so a personal setting can apply at once with `requiresReload: false`. (assumed)
- **Colour settings:** Foundry v14 core registers no colour setting of its own; the way to get its colour picker is a `DataField` as the setting's `type`: `type: new foundry.data.fields.ColorField({nullable: false, initial: "#0b0a13"})`. `ClientSettings#register` accepts a `DataField`, `DataModel` or function as `type` (`client/helpers/client-settings.mjs`); `SettingsConfig` uses that field's own input (`applications/settings/config.mjs`), and `ColorField#_toInput` makes a `<color-picker>` (a text box and a native colour swatch). The value is saved as `"#rrggbb"`; `game.settings.get` and `onChange` give a `Color` (a `Number` subclass whose `toString()` and `css` are `"#rrggbb"`), because the `Setting` document runs `type.initialize(type.clean(value))`. `ColorField` only accepts six-digit `#rrggbb` strings (`isColorString`). Guarded: without `ColorField` the colour setting falls back to a String text box. (assumed)
- **Reset buttons:** a setting whose data has `reset: true` gets a small Reset button beside its field (`settings.js`, `decorateSettingsConfig`), stripped before `game.settings.register` like `note`. It does what core's "Reset Defaults" does for one setting (`SettingsConfig#onResetDefaults`: set `checked` or `value`, fire `change`); nothing is saved until Save Changes. Foundry's `<range-picker>` and `<color-picker>` are `AbstractFormInputElement`s whose `value` setter redraws them and fires bubbling `input` and `change` (`client/applications/elements/form-element.mjs`). This is a difference from `void-coc7-modules`' `settings.js`; it can take the same flag when the two merge. (assumed)
- **Scope note:** every setting's hint ends with its note on its own italic line.
- **Reload:** a setting read once at `setup` needs `requiresReload: true`; one read at the moment it's used doesn't.
- **Action buttons:** a setting whose data has `button: { label, tooltip, onClick }` gets that button beside its field (`addActionButton`); unlike Reset it acts at once. Stripped before `game.settings.register` like `note` and `reset`. Used for Reset position. (confirmed)
- **A slider's value in words:** a setting whose data has `format: (value) => text` gets that text beside its slider, following it as it moves (`addValueText`; Auto-hide after reads "2 min 30 s"), because Foundry's range picker shows only the bare number. Stripped before registering like `note`.
- **Keys and the module id are permanent.** Renaming one throws away everyone's saved values.
- **Text is inline English**, no `lang/` files.
- **v14 API (checked, docs 14.370):** `game.settings.register(namespace, key, data)` and `game.settings.get(namespace, key)` are unchanged; scopes are `"world"`, `"user"`, `"client"`. `requiresReload` is used in the docs' example but isn't in the typed `SettingConfig` interface; it works on v14 in `void-coc7-modules`. `SettingsConfig` is an ApplicationV2 (through `CategoryBrowser`). (confirmed: Rollbox's setting registers and shows in v14 build 368's settings, no console errors)

## Gaps

Things the design needs that CoC7 can't do, or does differently, found in the CoC7 research; each was decided with the maintainer, and the design follows the decision.

**Gap 1. Missing skills get added to the sheet.** CoC7 adds the skill from its compendium (see "Skills the actor doesn't have"); the design says request at base value without adding it.
- A. Accept it: request by name; CoC7 adds the skill at its own base value and says so. All CoC7, but sheets change (NPCs collect skills) and CoC7's value can differ from Rollbox's table.
- B. Roll a raw value: `actor.runRoll({rollType: "R/MA", threshold})` at Rollbox's base value. Nothing is added. NPCs: fine (the Keeper rolls them anyway). Players: only through a standby card (needs `stanbyGMRolls` on), and the card shows "(20%)" without the skill name, so Rollbox's own request message has to name it.
- C. B for NPCs, A for player characters. Investigator sheets normally carry the full skill list, so the player case is rare.
- **Decided: C.** The design's "nothing added to the sheet" then holds for NPCs only.

**Gap 2. The item link starts an attack.** `@coc7.item` runs `actor.weaponCheck` → CoC7's melee or ranged attack card (with a "no target, proceed?" prompt unless the world setting `disregardNoTargets` is on) and ignores difficulty, dice and blind. The design keeps attacks out of Rollbox.
- A. Send the weapon's skill (`system.skill.main.name`, or `alternativ` when `usesAlternativeSkill`) as an ordinary skill check labelled with the weapon. Keeps difficulty, dice and blind; same path as the improvised weapon. Damage, if wanted, as a Foundry inline roll `[[/r 1D10]]` in the message, not CoC7's damage card (that needs the attack flow).
- B. Use `@coc7.item` as it is: CoC7's attack card, no difficulty or dice.
- C. Drop the Item flyout.
- **Decided: A.**

**Gap 3. "Pushed" can't be requested.** CoC7 pushes from the failed roll's own card: the owner clicks Push, CoC7 re-rolls on the same card, marks it pushed and blocks Luck. The link's `pushing` flag only changes the text; the new roll is an ordinary roll (Luck can be spent, it can be pushed again).
- A. Drop Pushed from the Check flyout; the Keeper tells the player to press Push on the failed card.
- B. Keep it as CoC7's Create link tool does: the request reads "… check - pushing", nothing more.
- **Decided: A.**

**Gap 4. Blind Sanity rolls.** The sanloss link ignores `blind`, and the v14 mode mismatch stops the card following the chat mode. There is no public way to create the Sanity card without a dialog.
- A. Drop Blind from the Sanity flyout.
- B. Keep the option but disabled, with a note "CoC7 can't do this yet".
- **Decided: A.**

**Gap 5. Combined rolls can't be blind.** The combined card is always public. Hidden difficulty does work (`0`).
- A. Turn Blind off and disable it while two or more checks are ticked.
- B. With Blind on, send separate blind checks instead of one combined roll (no longer one roll, so not a combined roll).
- **Decided: A.**

**Gap 6. Idea and Know can't be requested by link.** `characteristicCheck("idea")` fails; CoC7's Idea and Know cards come only from `runRoll({characteristic: "idea"})` or the player choosing the card type in the roll dialog.
- A. Send an INT or EDU check labelled "Idea" or "Know". Same numbers (p. 90: Idea is an INT roll); the result card says "Intelligence".
- B. Keeper side `runRoll({characteristic: "idea"|"know"})`: the card is titled "Idea Roll". Players only through a standby card.
- **Decided: A for everyone**: Idea and Know are sent as INT/EDU checks with a label, NPCs included. The Check flyout has no Attribute tab.

**Gap 7. Opposed ties outside combat.** CoC7 shows "Tie" with no winner; p. 91 gives the tie to the higher skill or characteristic, then a stalemate or re-roll.
- A. The Keeper settles ties: both sides' values are on the card ("Stealth (45%)").
- B. Rollbox adds a line after a tie naming the side with the higher value. Compares values, not dice, but needs CoC7's card data (internal) and goes beyond "CoC7 does the comparing".
- C. Switch the card to combat mode so the Keeper gets Advantage buttons on ties; the wording becomes attack wording.
- **Decided: A**, with the Opposed flyout's tie line naming the higher value before the card is made (from the two values only).

**Gap 8. Rolling NPC sides on cards automatically.** No public call. On the opposed card the Keeper's **Start rolls** also has to happen before players can roll.
- A. The Keeper clicks Start rolls (one click; it rolls the NPC sides).
- B. Rollbox clicks it on the Keeper's client: watch for the card it just asked for (`renderChatMessageHTML`, `flags.CoC7.load.as === "CoC7ChatOpposedMessage"` with both actor uuids), then click `[data-action="rollNoPlayers"]` once its listeners are attached. Internal (relies on CoC7's card HTML), guarded: if the button isn't found, the Keeper is told to click it.
- Either way, Start rolls also rolls for a character whose player is offline.
- **Decided: B, falling back to A.**

**Gap 9. Players can change the request in CoC7's roll dialog.** A link opens CoC7's dialog prefilled; the player can change difficulty, dice and card type, and a player with several characters can pick another one.
- A. Accept it (CoC7's normal behaviour; the card shows what was rolled).
- B. Use standby cards instead of links (Keeper triggers the check, options fixed, player clicks Roll): needs `stanbyGMRolls` on, the card is public unless blind, and it doesn't cover Sanity or combined rolls.
- **Decided: A.**

## Captures

The README's animation and the guide's captures are made from a running Foundry by `tools/capture/` in the development project (beside the module folder, like the e2e check; not in this repository, never shipped). Its `README.md` there has the camera spot, the commands and what puts the world back.

- **Format:** looping animated WebP, 1600×900, plus a few PNG stills; encoded in Chromium from its screencast, without ffmpeg.
- **One camera spot for every capture,** so the pictures line up across the guide: the test world's scene "Capture: Gas and coffee", the same view, token places, panel spot and chat column each time.
- **Where they go:** `media/<clip>.webp` in the module folder. The repository stores `media/` with Git LFS (`.gitattributes`), so a clone without Git LFS has only pointer files there; it never ships in the zip. Name a clip for the guide page and subject it shows (`check-skill`, `other-assist`).
- **Captions:** two lines of white text on a dark, see-through box at the top left: whose screen it is (**Keeper panel** or **Player panel**), then the step.

## Release checklist

Make the zip with the package script, never by hand. `release-check` runs `package` itself first, then does the smoke test on that fresh zip and checks the version, the zip's contents and `console.log` / `debugger` for you (see [docs/release-tools.md](release-tools.md)); the other items are by hand.

```
npm run release-check
```

- [ ] Version in `module.json` matches the newest `CHANGELOG.md` entry
- [ ] `compatibility` and the CoC7 `relationships` entry still correct (CoC7 minimum and verified 8.15)
- [ ] Tests pass, and the e2e check passes in Foundry
- [ ] Every internal API in use is in the registry
- [ ] The zip from the package script holds one top folder `keepers-rollbox` with `module.json` and `scripts/` — never `tests/`, `docs/`, `media/`, `package.json`, `package-lock.json` or `node_modules/`
- [ ] No `console.log` or `debugger` in `scripts/`
- [ ] The pull request or release notes say what changed, what the Keeper and players see, and what is untested

## Publishing (the maintainer releases)

Releases are made only by the maintainer, from the public repository `https://github.com/Voidworks-Foundry/Keepers-Rollbox`. Step by step: [recipes/make-a-release.md](recipes/make-a-release.md).

1. Run the release checklist above; bump the version in `module.json` and `download` (`…/releases/download/v<version>/keepers-rollbox-v<version>.zip`), and start the new version's `CHANGELOG.md` entry. `manifest` stays the raw `module.json` on `main` (`https://raw.githubusercontent.com/Voidworks-Foundry/keepers-rollbox/main/module.json`). Foundry checks for updates at the installed copy's `manifest` URL, so **`main`'s `module.json` is what every installed copy checks**: its version changes only at a release, and a release pushes `main` and creates the GitHub release with the matching zip together. Never push a version bump to `main` without its release.
2. Commit and push to `main`; CI runs the tests and the release check.
3. Right after the push, create the GitHub release: tag `v<version>` on `main`, title "Keeper's Rollbox <version>", notes with the manifest link, assets `dist/keepers-rollbox-v<version>.zip` and `module.json`; tick "Set as a pre-release" until 1.0.
4. Test the manifest link in Foundry (Install Module → Manifest URL).
