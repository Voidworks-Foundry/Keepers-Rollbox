# Settings code (`scripts/settings.js`)

Shared settings registration and the Configure Settings page layout. Each part defines its own settings as plain data; this file imports them, registers them in page order and lays the page out, so Foundry still shows every setting on one page. The file started as a copy of `void-coc7-modules` 1.0.10's; Rollbox's page differs: the five primary features' switches sit in a box on top, and each section below belongs to one feature and greys out while it is off, instead of each section having a master switch of its own. It also adds what the CoC7 module's copy doesn't have: the `reset: true` flag and its Reset buttons (`addResetButton`, `resetInput`), a setting's own action `button` (`addActionButton`), a slider's value read out beside it (`format`, `addValueText`), settings greyed out while a CoC7 theme is chosen (`foundryOnly`, `dimForTheme`), the Keeper's own settings hidden on a player's page (`keeperOnly`, `hideKeeperOnly`), and hiding Rollbox's settings from players while the Player Rollbox is off (`hideFromPlayer`).

What each setting does for the Keeper and players: the user guide's [Settings](../guide/settings.md) page.

**Status key:** *Confirmed* only when the [Internal API registry](DEVELOPING.md#internal-api-registry) says so or the maintainer checked it at the table, as marked. The registry has no row for settings registration or the page decoration, so those are **assumed** unless stated.

## Code

### `CONFIGS`, `FEATURES`, `SECTIONS`, `PAGE_ORDER` and `ALL_SETTINGS` (private constants)
- **What they are:** `CONFIGS` is every setting's data by key, gathered from the parts: `panel/settings.js` `PANEL_SETTINGS` and `APPEARANCE_SETTINGS` ([panel.md](panel.md#settings-settingsjs)), `shared/` `DICE_SETTINGS` ([shared.md](shared.md)), and the parts' declared lists (below), with `requiresReload: false` for all but the panel's switch and the Player Rollbox's (`PLAYER_CONFIGS`: the switch reloads, the features redraw each player's menu through `refreshPanel`). `FEATURES` is the box on top: `rollboxEnabled` ("Rollbox panel"), `rollboxPlayerRollbox` ("Player Rollbox"), `rollboxCombatPanel` ("Turn order and turn controls"), `rollboxGameplay` ("Gameplay rules"), `rollboxSetupCheck` ("Setup check at login"), with its note "Each section below belongs to one feature and is greyed out while that feature is off." `SECTIONS` is one entry per feature (five sections, each in its own box below the features box), `{ id, feature, title, groups: [[label, keys]], indent, menus }`, in page order:
  1. `panel`, "Rollbox panel" (follows `rollboxEnabled`): Look (`rollboxTheme`, `rollboxColor`, `rollboxTransparency`, `rollboxScale`, `rollboxNoticeScale`, `rollboxCardMeters`, the hidden `rollboxNoticePlaces`), Placement (`rollboxMovable`, `rollboxMenuSide`, `rollboxPanelLayer`, `rollboxAutoHide`, `rollboxAutoHideAfter`, the hidden `rollboxOffset`), Behaviour (`rollboxShowPlayers`, `rollboxEscapeClosesFlyout`, `rollboxSimplifiedDice`), Menus (`rollboxCheckOpensOn`, `rollboxListStyle`, `rollboxSpellTextTab`, `rollboxSpellTextCasting`); indented: Panel colour, Panel transparency, Auto-hide after.
  2. `playerRollbox`, "Player Rollbox" (follows `rollboxPlayerRollbox`): What players can do (`rollboxPlayerActions`, `…Checks`, `…Combined` indented, the hidden `…Sanity` and `…Luck`, `…Opposed`, `…Assist`), Each player's own (`rollboxRollMyAttacks`).
  3. `turnOrder`, "Turn order and turn controls" (follows `rollboxCombatPanel`): Your view (`rollboxTurnSelection`, `rollboxTurnOrderClick`).
  4. `gameplay`, "Gameplay rules" (follows `rollboxGameplay`): Starting a fight (`rollboxJoinRange`, `rollboxNoticeDraw`, `rollboxNoticeRange` and `rollboxNoticeDistance` indented), Firearms (`rollboxReadiedFirearms`, `rollboxBowsReadied` and `rollboxSwitchLosesReadied` indented), Melee (`rollboxMeleeReach`), Rolling (`rollboxAutoRollNpc`, `rollboxAutoRollAttacks`: Roll NPC attacks at once and Roll investigators' attacks at once, the Keeper's attacks, so they follow Gameplay rules, not the panel).
  5. `setup`, "Setup check" (follows `rollboxSetupCheck`): no setting, only the Check now menu (`menus: [CHECK_NOW.key]`).

  `PAGE_ORDER` is the feature keys, then each section's keys; `ALL_SETTINGS` the `[key, config]` pairs in that order. Foundry lists a module's settings in registration order (after its menus), so registering in `PAGE_ORDER` puts each setting next to its section's others. A setting registered hidden (`config: false`: `rollboxOffset`, `rollboxNoticePlaces`, `rollboxPlayerSanity`, `rollboxPlayerLuck`) has no form group, so the layout skips it. `rollboxOffset` and `rollboxNoticePlaces` hold where the panel and the notice cards were dragged, which has no field of its own. `rollboxPlayerSanity` and `rollboxPlayerLuck` are read by nothing: players have no Sanity or Luck tab (Sanity checks and Luck rolls are the Keeper's to call), and `player/` `playerFeatureOn` returns false for both before reading their settings (`KEEPER_ONLY`, [player.md](player.md)). They stay registered, hidden, because setting keys are permanent: dropping or renaming a key loses the value a world saved for it, and registered they keep it. The page order can change without touching keys or saved values.
- **Connects to:** `panel/settings.js` (imported directly: the panel's settings call the panel's own functions when they change, so `panel/index.js` re-exporting them would make an import cycle), `shared/index.js` (`DICE_SETTINGS`), the parts' declared lists (below), each read through its part's `index.js`, and `setup/` `CHECK_NOW`.
- **Could interact poorly with:** keys must never be renamed (saved values would reset). A key in a part's list but in no section would not be registered: the unit test's table of every setting catches it. **Assumed.**

### Declared settings and `declared(list, extra)` (private)
- **What they are:** a part's `SETTINGS` list made with `utils.js`' `declareSettings` ([utils.md](utils.md)): key, scope, type, default, section, label, hint, note, and choices or range. `declared()` turns a list into this file's section entries: `label` becomes Foundry's `name`, `key` and `section` are dropped, and `extra` (here `requiresReload`) is merged in. `option(key)` still answers with a declared default if a setting is ever read before `init`.
- **Connects to:** `flyouts/check/index.js`, `player/index.js`, `combat/index.js` (`GAMEPLAY_SETTINGS` from `encounter.js`, `FIGHT_SETTINGS` from `fight-state.js`, `TURN_SETTINGS`, `FIREARM_SETTINGS` from `readied-firearms.js`, `NOTICE_SETTINGS` and `DRAW_SETTINGS` from `notice-cards.js`, `NOTICE_PLACE_SETTINGS` from `notice-place.js`), `flyouts/action/index.js` (`REACH_SETTINGS` from `attack.js`, `SPELL_SETTINGS` from `spell-text.js`), `roll-requests/index.js` (`ATTACK_SETTINGS`), `setup/index.js`. Each list's `section` field names the page section it goes in (`panel`, `playerRollbox`, `turnOrder`, `gameplay`, `setup`); it is documentation only, `settings.js` places by `SECTIONS`.
- **Could interact poorly with:** nothing outside Rollbox. Importing these parts at `init` loads their modules early; none of them does anything at load time. **Assumed.**

### `registerSettings()` (called from `main.js` at `init`)
- **How it works:** For each setting registers `game.settings.register(MODULE_ID, key, { config: true, requiresReload: true, ...config })` with the `note`, `reset`, `button`, `format`, `foundryOnly` and `keeperOnly` fields removed (all six are Rollbox's own, for the page decoration). Registered in page order (`ALL_SETTINGS`), then the Check now menu (`setup/` `registerCheckNowMenu`). A setting can turn off `requiresReload` in its own data (every look and placement setting and Simplified dice UI do). A setting's `type` may be a Foundry `DataField` instance (`rollboxColor` uses `ColorField`), which Foundry v14 accepts and shows with that field's own input. Any other field in the data, such as `range` or `onChange`, goes to Foundry unchanged.
- **Connects to:** `game.settings` (`ClientSettings#register(namespace, key, data)`; v14 docs list scopes `"world"`, `"user"`, `"client"`), `utils.js`.
- **Could interact poorly with:** nothing known. Registered keys and scopes are permanent. `requiresReload` appears in the v14 docs' register example but not in the typed `SettingConfig` interface; it works in `void-coc7-modules` on v14. **Assumed.**

### `decorateSettingsConfig(app, html)` (the `renderSettingsConfig` hook handler)
- **How it works:** Returns unless `html` is an `HTMLElement`. On a player's client while the Player Rollbox is off it only hides Rollbox's settings (`hideFromPlayer`, below). Otherwise: on a player's client hides the Keeper's own settings (`hideKeeperOnly`); for every setting adds its italic scope note (under its hint; a setting without a hint gets a `p.hint` made for the note) and the Check now menu's; for every setting whose data has `reset: true` adds a Reset button; for every setting with a `button` adds that action button; for every setting with a `format` adds a line beside its field showing the value as `format` reads it (`data-coc-value`, following the slider's `input` and `change`: Auto-hide after's "2 min 30 s"); then the feature box (`addFeatures`) and each section's box after the one before (`addSection`); then greys out the `foundryOnly` settings while a CoC7 theme is chosen (`dimForTheme`, below). Repeated renders don't duplicate anything, because existing elements are detected (`data-coc-scope`, `data-coc-reset`, `data-coc-action`, `data-coc-value`, `data-coc-section-box`).
- **Connects to:** the settings form DOM (`[name="<MODULE_ID>.<key>"]`, a menu's `[data-key="<MODULE_ID>.<key>"]`, `.form-group`, `.hint`), Foundry's `h4.border` and `.hint` styles and its colour variables (`--color-border-highlight`, `--color-border-light-tertiary`, `--color-text-accent`, `--color-text-secondary`, `--font-body`); `utils.js` (`isKeeper`), `player/` (`playerRollboxOn`). Internal API registry ("Configure Settings' module section as plain `.form-group`s").
- **Could interact poorly with:**
  - A Foundry update that changes the form markup (no box would be drawn; every setting still shows and works); other modules that reorder form groups. **Assumed.**
  - `void-coc7-modules`, which runs its own copy of the older code on the same page with `data-coc-*` markers (`h4[data-coc-section]` headings of its own). Rollbox's boxes are marked `data-coc-section-box` and hold only Rollbox's form groups; each module looks only inside its own settings. Seen in e2e (the CoC7 module's headings are on the same page, untouched). **Assumed** until checked at the table.

### `addFeatures(html, formGroup)`, `addSection(html, section, formGroup, after)`, `makeBox`, `firstRollboxGroup`, `sectionScope` (private)
- **How it works:** `addFeatures` puts a box (`div[data-coc-section-box="features"]`, a full border in Foundry's highlight colour, `--color-border-highlight`) before the first of Rollbox's form groups (a menu is drawn first) and moves the feature switches' form groups into it, under an `h4.border` "Features" heading with its note on the right. `addSection` does the same for one section after the box before it (or, when nothing was drawn yet, before the first Rollbox group): a box with a plain full border (`--color-border-light-tertiary`), its `h4.border` heading (`data-coc-section` = the section id) with "Personal · follows Rollbox panel" (`sectionScope`: Personal, Keeper or Mixed from the section's settings' scopes; a menu counts as Keeper) on the right, then each group: a small label line (`p[data-coc-group]`, capitals, Foundry's accent colour) and its form groups; settings in `indent` get `padding-left: 1.5rem`; the section's menus go last. A group or section with nothing shown (on a player's page, e.g. Turn order and turn controls) is left out. The feature's tick box (`[name="<MODULE_ID>.<feature>"]`) greys the box to `DIMMED_OPACITY` (0.45) while unticked, following its `change` event before Save (`data-coc-section-dimmed`); with no tick box on the page (a world setting on a player's page) the box is never greyed. Display only: nothing is disabled and nothing saved, and each part reads its own switch when it runs.
- **Connects to:** `FEATURES`, `SECTIONS`, `CONFIGS`.
- **Could interact poorly with:** Foundry's search box, which hides single form groups (`hidden`) but not Rollbox's boxes and labels: while searching, the boxes stay with only the matching settings in them. **Assumed.**

### `hideKeeperOnly(keys, formGroup)` (private)
- **How it works:** on a player's client (with the Player Rollbox on), the settings marked `keeperOnly: true` (Show the players when nothing is selected, `panel/settings.js`; At each new turn and Left click in the turn order, `combat/turn-order.js`), which do nothing on a player's panel, get `display: none` (Foundry's search doesn't undo an inline style) and `data-coc-keeper-only`, so the layout skips them.
- **Connects to:** the `keeperOnly` flag in the settings' data.
- **Could interact poorly with:** nothing known. Seen in e2e on the Player's page. **Assumed.**

### `dimForTheme(html, keys, formGroup)` (private)
- **How it works:** The settings marked `foundryOnly: true` in their data (Panel colour and Panel transparency, `panel/settings.js`) only change the Foundry theme: Art Deco and CoC7 minimal draw CoC7's own solid look. While the Theme field (`rollboxTheme`) holds anything but `foundry`, their form groups are dimmed to `DIMMED_OPACITY` (0.45), and they follow the field's `change` event, so choosing a theme greys them before Save. Their hints start "Foundry theme only." It is a visual dimming only; the fields still work. Each group carries `data-coc-theme-dimmed`. A section's own greying is on its box, not the group, so the two add up and neither undoes the other.
- **Connects to:** the `foundryOnly` flag in the settings' data; the Theme field's `select`; `addSection`.
- **Could interact poorly with:** Foundry's form markup changing (no field or form group: nothing dims). **Assumed.**

### `hideFromPlayer(html)` (private)
- **How it works:** on a player's client while the Player Rollbox is off, `decorateSettingsConfig` hides Rollbox's tab and section in Configure Settings (`[data-tab="keepers-rollbox"]`, `[data-category="keepers-rollbox"]`, Foundry v14's category browser) and every Rollbox `.form-group`, with an inline `display: none` (Foundry's search box only sets `hidden` on single settings), so nothing of Rollbox shows for players. Nothing else is decorated then.
- **Connects to:** `player/` `playerRollboxOn`, `utils.js` `isKeeper`.
- **Could interact poorly with:** a module that rebuilds the settings window's tabs after render (the tab would show again; its settings still do nothing without a panel). **Assumed**; the hiding itself was seen working in the end-to-end check.

### `addScopeNote(group, note)` (private)
- **How it works:** Appends an italic block-level span with the note inside the setting's `.hint`, once.
- **Could interact poorly with:** settings with no hint element get no note. **Assumed.**

### `addResetButton(input, value)` (private)
- **How it works:** Adds a small `<button type="button" data-coc-reset>Reset</button>` (with a tooltip) at the end of the setting's `.form-fields` (or beside the input if there is none), once. Driven by `reset: true` in the setting's data, so the CoC7 module can use the same flag after a merge. Rollbox marks Theme, Panel transparency, Panel colour and Panel size. `type="button"`, so a click never submits the form.
- **Connects to:** `resetInput`; the setting's own `default` in its data.
- **Could interact poorly with:** Foundry's form markup changing (no `.form-group`: no button). **Assumed.** `void-coc7-modules` running the same code on the same page: each looks only inside its own settings' form groups. **Assumed.**

### `addActionButton(input, { label, tooltip, onClick })` (private)
- **How it works:** A setting's own action, from `button: { label, tooltip, onClick }` in its data: a `<button type="button" data-coc-action>` with that label and tooltip at the end of the setting's `.form-fields`, once. Unlike Reset it acts at once when clicked (there is no form value to save). Rollbox uses it for **Reset position** beside Allow moving the panel (`resetPosition()`, [panel.md](panel.md)). Not in `void-coc7-modules`' copy; it can take the same flag after a merge.
- **Connects to:** the setting's `button` data.
- **Could interact poorly with:** Foundry's form markup changing (no `.form-group`: no button). **Assumed.** **Confirmed** at the table: the button shows beside the tick box and puts the panel back at once.

### `addValueText(input, format)` (private)
- **How it works:** A setting's `format` function (Auto-hide after's `durationText`, `panel/settings.js`) gives a line of text beside its field (`span[data-coc-value]`, at least 6em wide), what the bare number means ("2 min 30 s"). It is written once at render and again on the field's `input` and `change` events, so it follows the slider as it moves; a `format` that throws leaves it empty. Once per field.
- **Connects to:** Foundry's `<range-picker>` (its `value` and its `input` / `change` events); the setting's `format` data.
- **Could interact poorly with:** Foundry's form markup changing (no `.form-group`: no line). **Assumed.**

### `resetInput(input, value)` (private)
- **How it works:** Puts the default into the form field only, the way Foundry's own "Reset Defaults" button does (Foundry build 370 `SettingsConfig#onResetDefaults`): `checked` for a checkbox, otherwise `value`, then a `change` event. Foundry's `<range-picker>` and `<color-picker>` redraw and fire their own `input` and `change` events when their `value` is set (`AbstractFormInputElement`). Nothing is saved until the Keeper presses Save Changes, which then calls the setting's `onChange` as usual. Other settings' fields are untouched.
- **Connects to:** Foundry's form elements (build 370 `client/applications/elements/form-element.mjs`).
- **Could interact poorly with:** nothing known. **Assumed.**
